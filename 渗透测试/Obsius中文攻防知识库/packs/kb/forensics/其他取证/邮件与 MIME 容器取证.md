# 邮件与 MIME 容器取证

压缩包、文档类容器见 [[forensics/隐写与信号/通用隐写结构与容器分析.md|通用隐写结构与容器分析]]；嵌套压缩包与已知明文恢复见该文 §5.3；编码识别见 [[misc/编码解码/编码与二维码.md|编码与解码基础]]。

邮件是**容器**而不是**文本**：一个 `.eml` 等于「头部一张图 + 若干 part 的树」。绝大多数失分不是看不懂邮件，而是把整个文件当文本读完就下结论，漏掉深层的 part 与它真实的魔数。

## 测试面

| # | 方向 | 判据（怎么发现） | 动作 |
|---|---|---|---|
| 1 | 头部与投递链 | 存在多条 `Received:`、`Message-ID`、`X-Mailer` 等客户端注入头 | 按 `Received` 自下而上还原投递路径，比对发件域与 `Return-Path` |
| 2 | MIME part 树 | 出现 `Content-Type: multipart/*` 与 `boundary` | 递归展开 part 树，逐个记录 type / transfer-encoding / charset / 解码后长度 |
| 3 | 正文载荷 | 正文夹带与语境无关的长 token（4 的倍数、纯 `A-Za-z0-9+/=`），或中文里嵌一段纯 ASCII | 单独取出做编码识别，**先当密钥/口令候选**，不当答案 |
| 4 | 附件提取 | part 头有 `filename=` / `name=` 或 `application/octet-stream` | 取**解码后的原始字节**落盘，文件名不信任扩展名，立刻判魔数 |
| 5 | 传输编码与字符集 | 声明 `base64` / `quoted-printable`，或 `charset=gb18030`、`gbk`、`big5` | 固定顺序：剥传输编码 → 按声明 charset 解 → 不符再穷举中文编码 |
| 6 | 伪造与仿冒痕迹 | 显示名像机构但地址是免费邮箱；`Reply-To` ≠ `From`；`X-Originating-IP` 是内网/环回 | 把身份字段并列对照，域不一致即仿冒叙事 |
| 7 | 附件本体判定 | 扩展名与头部魔数不符；`file` 报 `data` | 以魔数为准，按真实类型重新路由分析 |
| 8 | 嵌套容器链 | 每层解出的对象本身仍是压缩包/文档容器 | 递归解包，逐层记「层号 + 文件名 + 魔数 + 解码方式」 |

## 1. 头部与投递链

**前置**：拿到的是含完整头的原始 `.eml`（不是截图或正文摘录）；`grep` / `awk` / `python3` 至少有一个可用。

**判据**：存在多条 `Received:`；或出现 `X-Mailer`、`X-Originating-IP`、`X-QQ-FEAT` 一类客户端注入头，且与实际发件域矛盾。

**动作**：先把身份类字段一次拉平再读。

```bash
grep -nE '^(Received|Return-Path|From|Reply-To|Message-ID|X-Mailer|X-Originating-IP|Authentication-Results):' msg.eml
```

`Received` 是逐跳**自下而上**追加的：最上面一条是最后一跳（收件方），最下面一条才是真正的出口。要还原来源就**从最下一条往上读**，反过来读会得到完全错误的结论。

**不成立**：只有单条 `Received` 且与发件域一致、无客户端注入头 → 头部不是载体，转 §3 看内容侧。

**降级**：没有 `grep` 的交替支持时，用 `awk 'BEGIN{RS=""} {print}'` 按空行切出头部块再逐块看；或直接在 Python 里读 `message.items()`。

## 2. MIME part 树

**前置**：文件是合规则 MIME；`python3` 标准库 `email` 即可，无需第三方包（`munpack` / `ripmime` 可选但非必需）。

**判据**：出现 `multipart/mixed`、`multipart/alternative`、`multipart/related` 之一，说明存在嵌套——尤其 `mixed` 套 `alternative` 这种双层结构，正文往往有 `text/plain` 与 `text/html` 两份，附件挂在 `mixed` 下层。

**动作**：打印整棵树，标出每个节点的类型、传输编码、处置方式与**解码后真实长度**。解码后长度是关键——声明为文本却解出十几 KB，基本都是二进制载荷。

```python
import email, email.policy
m = email.message_from_bytes(open('msg.eml','rb').read(), policy=email.policy.default)
def walk(p, d=0):
    payload = p.get_payload(decode=True) or b''
    print('  '*d, p.get_content_type(),
          p.get('Content-Transfer-Encoding'),
          p.get('Content-Disposition'),
          len(payload))
    if p.is_multipart():
        for s in p.iter_parts():
            walk(s, d+1)
walk(m)
```

**不成立**：`multipart` 字样只出现在正文叙述里（被引用但未定义对应 boundary），或 boundary 分隔行在文件中根本不存在 → 按单 part 处理。

**降级**：环境无 Python 时，按 `--<boundary>` 行手工切分；boundary 可能带引号或被改写，以**文件里实际出现的分隔行**为准而不是头里声明的值。

## 3. 正文载荷

**前置**：part 树已展开；至少一个正文 part 能解出可读文本。

**判据**：正文出现与语境无关的长 token —— 长度是 4 的倍数、字符集恰为 `A-Za-z0-9+/=`；或一段通顺中文里孤零零嵌着一串纯 ASCII 字母数字，紧邻句读但不构成句子。

**动作**：把这类串单独切出，先做编码识别（看字符集与长度），常见是 base64 / hex / urlencode。**关键纪律：先当密钥、口令或下一层的输入候选，不要当最终答案。** 判定它是不是答案只有两条路——符合题目声明的 flag 格式，或它作为密钥真的解开了下一层。两条都不满足时，它只是中间产物，登记为线索而不是结论。

同时注意 `text/plain` 与 `text/html` 两个 part 是否在**同一位置**出现同一串：一致说明是刻意埋的载荷而非渲染残留。

**不成立**：该 token 是签名块、备案号、邮箱、电话等有明确语义的字段 → 不是载荷，回 §4 找附件。

**降级**：整段字符集混杂无法整体解码时，按行或按空白切成候选片段逐个试，不要对整段强行 `b64decode`。

## 4. 附件提取

**前置**：MIME 中至少一个 part 带 `Content-Disposition: attachment` 或 `filename=` 参数。

**判据**：part 头出现 `filename=` / `name=`，或类型为 `application/octet-stream`。

**动作**：取 `part.get_payload(decode=True)` 的**解码后原始字节**写盘——不要写 `get_payload()` 的 base64 文本。文件名以声明的 `filename` 为初值但**不信任扩展名**，写盘后立刻 `file` + 前 32 字节 hex 双判。之后按 §7 路由。

**不成立**：附件为空、为零字节占位、或只是一张内嵌签名图（`image/*` 且尺寸很小）→ 载体在正文，回 §3。

**降级**：`get_payload(decode=True)` 抛异常（传输编码畸形、行长度非法）时，取原始串自行 `base64.b64decode(..., validate=False)`，或先删掉所有非 base64 字符再解。

## 5. 传输编码与字符集

**前置**：part 头存在 `Content-Transfer-Encoding` 或 `charset` 参数。

**判据**：解码后仍是乱码；或声明 `charset=gb18030` / `gbk` / `big5`，按 UTF-8 读失败或出现大量替换符。

**动作**：顺序固定，不要跳步——

1. **先剥传输编码**：`base64` 或 `quoted-printable`。QP 的 `=XX` 与软换行 `=\r\n` 必须处理，否则会残留等号。
2. **再按声明 charset 解码**。
3. **不符时穷举**：`gb18030` → `big5` → `cp437` → `latin-1`，取能产出合法中文的那个。`gb18030` 是 `gbk`/`gb2312` 的超集，中文场景优先用它。

**不成立**：所有候选 charset 都解不出可读文本 → 该 part 不是文本，是二进制载荷，按 §7 判形态而不是继续换编码。

**降级**：无 `chardet` 时用 `bytes.decode(enc, errors='strict')` 逐编码试。注意 `gb18030` 对几乎任意字节序列都不抛错，**单靠"不报错"不能证明解对了**，必须配合可读性判断；反之 `utf-8` / `big5` 报错则是强否定信号。

## 6. 伪造与仿冒痕迹

**前置**：头部可读且包含身份类字段。

**判据**：发件显示名像机构或品牌但实际地址是免费邮箱；`Reply-To` 与 `From` 不同域；`X-Originating-IP` 是内网段或环回地址；`Authentication-Results` 缺失，或 SPF / DKIM / DMARC 全为 fail。

**动作**：把 `From` / `Reply-To` / `Return-Path` / `Message-ID` 的域并列排开对照。域不一致本身就是"钓鱼"叙事的一部分——这类题常把仿冒当作**题面线索**，指向"相信正文的诱导、去看附件"，而不是要求真的去请求任何外部地址。任何情况下都不要对邮件里的链接发起实际访问。

**不成立**：三者域一致且有通过的 SPF/DKIM → 不是仿冒场景，按普通附件题处理。

**降级**：头被剥离（只留正文）时，改从正文措辞、落款与链接域名判断，但结论只能作为旁证。

## 7. 附件本体判定

**前置**：附件已按原始字节落盘。

**判据**：扩展名与头部魔数不符——例如声明为 `.docx` 但前 4 字节不是 `50 4b 03 04`；或 `file` 直接报 `data`。

**动作**：`file` 与 hex 双判，**不符时以魔数为准**，按真实类型重新路由：PE（`MZ`）→ 二进制分析；zip/7z/rar → §8 递归；无可识别魔数 → 先按 §5 试"它是不是被某种编码/简单异或改写过"，再考虑加密载荷。

一个高频形态：**扩展名是文档、内容是被整体改写过的二进制**。此时用已知格式头做差值往往能直接得到变换参数——把观测头与目标格式头的对应字节逐一异或，若结果呈短周期重复，说明是重复密钥异或；再用该密钥解完整文件，并用解出后的目录结构（而非仅前几个字节）验证正确性。

**不成立**：扩展名与魔数一致 → 正常附件，按该类型常规流程处理。

**降级**：无 `file` 时用前 16 字节对照常见魔数表（zip `50 4b 03 04`、PE `4d 5a`、PDF `25 50 44 46`、PNG `89 50 4e 47`、ELF `7f 45 4c 46`、7z `37 7a bc af`、rar `52 61 72 21`）。

## 8. 嵌套容器链

**前置**：某层解出的对象本身是压缩包或文档容器。

**判据**：每层文件头为上表任一容器魔数；或解出的文件再次 `file` 报出压缩/文档类型。

**动作**：递归解包并**逐层记账**：层号、文件名、魔数、解码方式、该层用到的密钥或口令。终止条件是"本轮没有产生任何新的可解对象"，而不是"解出看起来像答案的东西"。压缩包细节（伪加密标志位、CRC 失败、缺头补头、ZipCrypto 已知明文）直接查 [[forensics/隐写与信号/通用隐写结构与容器分析.md|通用隐写结构与容器分析]] §5.3，不要重写一套。

**不成立**：解出的对象魔数完全不可识别，且 §5 的编码与编码穷举都不成立 → 停止递归，转为加密载荷处理。

**降级**：层数多时脚本化，用集合记录已处理对象的哈希以避免循环解包（自引用容器存在）；不要把 `7z x` 的返回码当唯一成功判据，CRC 报错但文件已写出是常见情形。

## 9. 已验证路径、适用条件与常见坑

**适用条件**：拿到的是单文件邮件（`.eml` / `.msg` / `.pst` 导出件）或邮件本体被塞进压缩包；有 `python3` 标准库或任一文本过滤工具。缺任何一项时按各节的降级路径走，不必换整套方法。

**已验证路径（按序走，逐层坐实）**：

1. 展开 part 树，记下每个节点的 type / 编码 / 解码后长度；
2. 剥传输编码 → 按声明 charset 解 → 不符再穷举中文编码；
3. 正文判读：可疑长串按密码学候选处理；
4. 附件按**解码后原始字节**落盘，`file` + hex 双判魔数；
5. 魔数不符则按真实类型路由；容器则递归，逐层记账；
6. 每层结论都必须由字节级证据支撑（魔数、长度、内部结构），不能只凭"解出来像"。

**常见坑**：

- **把整个 `.eml` 当文本 `cat`**：正文是 base64 的，直接看只能看到编码串，看不到附件与深层 part。
- **`Received` 顺序读反**：自上而下读会把最后一跳当成源头。
- **只信声明的 charset**：声明与实际不符极常见；`gb18030` 对任意字节都不抛错，不能用"不报错"当解对了。
- **拿 `get_payload()` 而不用 `get_payload(decode=True)`**：前者是 base64 文本，写盘得到的是编码后内容，后续所有魔数判断都会错。
- **扩展名当类型**：`application/octet-stream` 与伪装扩展名是这类题的常态，魔数优先。
- **把正文里的密钥串当成答案**：这是本题型最常见的误判，见 §3 的判据纪律。
- **`7z x` 返回非零就以为失败**：CRC 报错但文件已写出很常见，要按落盘结果判断。

**复现要点**：记录每层「文件名 + 魔数 + 解码方式 + 用到的密钥」，使得任何人可以从原始附件逐步重跑得到同一结果；中间产物按层命名保存，不要在原件上就地改写。
