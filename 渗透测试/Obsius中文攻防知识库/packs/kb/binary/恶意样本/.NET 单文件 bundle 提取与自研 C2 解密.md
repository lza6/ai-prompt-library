## 判据速查

| 卡在哪 | 首选手法 | 去哪节 |
|---|---|---|
| .NET 单文件 exe，按尾部 `[sig][ver][count]` 解析 bundle header 失败 | 用 assembly 名 + MVID GUID 做内容指纹，扫 `MZ` 逐个切尾验证 | §1 |
| 内嵌 assembly 已拿到，但 `command -v ilspycmd monodis` 为空 | **别急着自写**：先 `apt-get update`（容器无索引态会报 "Unable to locate package"），再 `pip3 install dnfile dncil`；0.4 起已内置 | §2 |
| 确实只能自写 metadata 堆解析 + IL opcode 表 | 只盯 `ldstr`；**`0xFE` 前缀必须消耗操作数**，交付前用 dncil 逐条交叉校验 | §2 |
| 怀疑「固定 IV / 每帧重跑 KSA」，正在比公共前缀长度 | 别比 lcp（区分不出来），改用双流异或 + 长度非块长整数倍 | §3 |
| 长度头切帧在一侧立刻失败（读到零长或荒谬值） | 先放行零长心跳帧并多试起始偏移，再怀疑自己，而非直接断定协议不对称 | §4 |
| 命令行哈希输出是空格分隔字节对，要转成紧凑串 | 脚本一次性提取 + 断言定长 + 直接 print，禁止人工转录 | §5 |

## 1. 单文件 bundle 的内嵌程序集挖取（已验证路径 + 适用条件）

**前置（适用条件）**：样本是 `PE32/PE32+` 且含 `.CLR_UEF`、`.net` 相关节区名，或存在 `I LLINK` / `runtimeconfig.json` / `deps.json` 等字符串——这些是 single-file host 的指纹，说明真正的托管代码以**完整 PE 片段**形式内嵌，而不是普通资源。

**判据**：不要假定 bundle header 在文件末尾完好。安装器型样本、被追加数据的样本，尾部 header 会被整体覆盖，此时按 `[64 位签名][版本][文件数]` 顺序读会读出明显荒谬的 count 或直接越过文件末尾。**这个失败本身**就是判据：改用内容指纹。

**动作**：

```python
import re, struct

data = open('sample.exe','rb').read()

# 1) 先定位内嵌 assembly 名的出现处（比死背不同 SDK 版本的签名更稳）
for m in re.finditer(rb'[A-Za-z0-9_.]+\.dll', data):
    print(hex(m.start()), m.group())

# 2) 名字之后通常紧跟 [偏移][大小][压缩标志][MVID GUID]
#    把该位置前后 100 字节 dump 出来人工确认字段布局
```

拿到 assembly 名与 **MVID GUID** 后，用「三重指纹」定位真正的 PE 起点：

```python
import re, struct

def carve_inner_pe(data, guid_bytes, mz_hits=200):
    out = []
    for mz in [m.start() for m in re.finditer(rb'MZ', data)][:mz_hits]:
        # 读 COFF 头拿节表，按 (PointerToRawData + SizeOfRawData) 切出真实尾部
        try:
            e_lfanew = struct.unpack_from('<I', data, mz + 0x3c)[0]
            if data[mz + e_lfanew:mz + e_lfanew + 4] != b'PE\0\0':
                continue
            nsec = struct.unpack_from('<H', data, mz + e_lfanew + 6)[0]
            opt_size = struct.unpack_from('<H', data, mz + e_lfanew + 20)[0]
            sec = mz + e_lfanew + 24 + opt_size
            end = 0
            for i in range(nsec):
                raw_size = struct.unpack_from('<I', data, sec + i*40 + 16)[0]
                raw_ptr  = struct.unpack_from('<I', data, sec + i*40 + 20)[0]
                end = max(end, raw_ptr + raw_size)
            blob = data[mz:mz + end]
        except Exception:
            continue
        # 三重指纹：MZ + .NET metadata 签名 BSJB + 目标 MVID
        if b'BSJB' in blob and guid_bytes in blob:
            out.append((mz, len(blob), blob))
    return out
```

判据收敛点：**`BSJB` 是 .NET metadata 流的根签名**，出现在每个托管模块的 `#~` 之前；再叠加 bundle header 里读到的 MVID，三个条件同时命中基本不会误切。切出的片段直接当独立 PE 处理（`file` 应报 `Mono/.Net assembly`），喂给任意 .NET 解析器都成立。

**不成立**：若扫完所有 `MZ` 都没有任何片段同时含 `BSJB` 与目标 GUID，说明内嵌程序集被压缩（bundle 头的 compression 标志非 0）。此时不要继续猜偏移，改为**运行时取镜像**。

**降级**：压缩型 bundle 的静态提取性价比极低。容器里无 Windows 时优先「在隔离容器内执行一次并抓取落地文件」；有 Windows 环境时用 `pe-sieve` 在进程启动后 dump 内存镜像，比逆向 deflate 解包逻辑快一个数量级。要取样执行必须限定在隔离环境，不可在分析机直接跑。

## 2. metadata + IL 快速反汇编（先确认工具链真的没有，再降级）

**前置**：已切出内嵌 assembly。

**⚠️ 先做这三步再谈「没有工具」**（2026-10-28 复盘：0.3 镜像那次「工具链全缺」
有三处是调用姿势问题，不是能力上限）：

1. `command -v monodis ilspycmd` 为空时，**不要直接断定源里没有** —— 镜像
   构建末尾执行了 `rm -rf /var/lib/apt/lists/*`，容器处于**无 apt 索引**态，
   任何 `apt-get install X` 都回 `E: Unable to locate package X`。先
   `apt-get update`（国内约 3 分钟，**要单独给足超时**），再装 `mono-utils`。
2. **pip 白名单不约束容器**。`core/runtime/recovery.py` 的 pip 白名单只管宿主
   `tools/venv`（源码里写死 `runtime not in {host,wsl} → denied`）。容器内
   `pip3 install --break-system-packages dnfile dncil` 直接可装，两个都是纯
   Python wheel。**pypi.org 在国内会超时，加 `-i https://pypi.tuna.tsinghua.edu.cn/simple`。**
3. `ilspycmd` 不要用 `dotnet tool install`（runtime-only 环境无 SDK，报
   `sdk-not-found`）。直拉 NuGet nupkg 解压后 `dotnet <ilspycmd.dll>` 执行。

镜像 `pentest-box:0.4` 起已内置这三件（`monodis` / `ilspycmd` / `dnfile`+`dncil`），
正常情况**直接可用**，不需要任何降级。

**判据**：文件里同时存在 `BSJB` 与节名 `.text`，且 `strings` 能看出 C# 命名空间形态（`System.Runtime`、`<Module>`、`<PrivateImplementationDetails>`）。此时目标不是还原完整 C#，而是**只抽取字符串常量与其引用点**——密钥、端口、命令字通常都是 `ldstr` 立即数。

**动作**（按顺序，每一步都能独立产出结论）：

```text
0. 优先用现成工具（0.4 起内置）：
     monodis <dll>                  # IL 反汇编，等价 ildasm
     ilspycmd <dll>                 # 直接出 C# 源码，最快
     python3 -c 'import dnfile'     # 程序化取元数据
1. 定位 metadata 根：搜 b'BSJB'，其后 4 字节版本长度，
   再读 [verLen][version][flags][#Streams] 得到流头数组。
2. 逐个流头读 [offset][size][name\0]（4 字节对齐）。
   只需要两个堆：
     #US  = 用户字符串堆，UTF-16，每项前置 compressed length
     #Strings = 标识符堆，UTF-8
3. 若 #US 项数极少（个位数），直接把每条打印出来 —— 这是最快的答案。
4. 定位方法体：MethodDef 表（0x06）→ RVA → 节内偏移 → tiny/fat 头
   → 按 opcode 表反汇编，只记录 ldstr（0x72，后跟 4 字节 user-string token）
   与 call/callvirt（寻找对称加密 API）。
```

要点：**先读 `#US` 堆，再决定要不要反汇编方法体**。字符串堆里条目很少时（个位数到几十条），直接列出就能拿到密钥/端口/命令字，不必写 opcode 表。`#US` 项编码是 `[compressed length][UTF-16LE 数据][1 字节 flag]`，flag 末位为 1 表示字符串含特殊字符。

**不成立**：若 `#US` 堆条目极多且全是乱码、或方法体几乎全是 `switch` 分发，说明 IL 被控制流混淆——此时硬读 opcode 无意义，转 `de4dot` 脱壳或改用 AsmResolver 按 API 调用筛方法。

**降级（自写解析器时的硬要求）**：只有上面三步都走不通（离线、无源、被策略禁）才自写。

**必须遵守两条**，否则会重演 2026-10-28 那次事故：

- **`0xFE` 前缀指令必须消耗操作数**。`initobj`/`constrained.`/`ldftn`/`sizeof`/
  `ldarg`/`ldloc` 都带操作数（4 字节 token 或 2 字节槽位）。只打印前缀不读操作数
  → **后续整段指令流错位**，而且不报错、不崩、末条仍以 `ret` 收尾、方法数零异常。
  真实样本 `Server.dll` 有 6 处，全在 async `MoveNext`（C2 主循环）。
- **未登记的操作码要停下来标 UNKNOWN**，不能 `SZ.get(nm, 0)` 当无操作数放过去。

**交付前必须与 dncil 交叉校验**（真值随时可得）：

```bash
python scripts/verify_ildis.py --ildis <你的解析器.py> \
    --dll <样本.dll> --dncil-json <预采真值.json>
```

判据是**指令起始偏移序列逐条相等**，不是只比条数（错位后重新同步也可能凑出
同样条数），也不是只比末条偏移（错位 4 字节后末条仍可能落在 `ret` 上）。

## 3. 判定流密码是否「每帧重跑 KSA」（易错坑：别用公共前缀长度）

**前置**：无。这是协议结构层面的判断，与语言、算法无关。

**判据**：三条，强度递增。

| 判据 | 观察 | 结论 |
|---|---|---|
| A（排除法） | 密文长度等于长度头声明的载荷长度，且该长度**不是块长（16）的整数倍** | 不可能是 ECB/CBC+padding，只能是流密码或流模式 |
| B（决定性） | 取两条**明文不同**的密文逐字节异或，`ct1 XOR ct2` 中出现可读片段或显著低熵 | 两帧共用同一 keystream 起点 → 每帧重置、无 IV、无 nonce |
| C（旁证） | 多条**明文相同**的响应，其密文**整段逐字节相同** | keystream 与明文都相同，与每帧重置一致 |

**关键易错点**：`最长公共前缀（lcp）远小于帧长` **不能**用来区分「每帧重跑」与「固定 IV 块密码」。当两条明文只在尾部不同时，固定 IV 的 CBC 同样给出「密文公共前缀 = 明文公共前缀按块对齐后的长度」，与每帧重置的观察**完全一致**。用 lcp 判别会把人误导向块密码分支。

**动作**：先做判据 A 排除块密码，再做判据 B 的双流异或 + crib drag（拿目录头、卷标行、路径串等已知片段去撞）。确认 keystream 复用后**不要去找 IV/nonce**，每帧独立解密、keystream 从计数器初值起算。注意可能存在的双层结构（如 `ct = XOR_rolling(RC4(pt, K), X)`）：先剥异或层再 RC4，顺序反了得到的是另一种乱码。

```python
# 判据 B：两帧异或应等于两段明文异或
d = bytes(a ^ b for a, b in zip(ct1, ct2))
print(d[:64])     # 出现可读片段/显著低熵 → keystream 复用
```

**不成立**：若 `ct1 XOR ct2` 呈高熵且 crib drag 拖不出任何可读片段，说明 keystream 未复用（每帧换 key/nonce 或存在真 IV），必须回样本找 IV/nonce 来源，不要再按「无 IV」硬解。

**降级**：样本不可解时，若存在「明文相同」的帧组，取该组任一条密文与已知明文异或得到完整 keystream，可直接用于其它同起点帧的前 `min(len)` 字节——不需要样本。

## 4. 长度头切帧失败时先怀疑自己：零长心跳会伪装成「协议不对称」（常见坑）

**前置**：无。反向连接型远控（服务端被动监听、攻击者主动连入）常被误认为「客户端与服务端协议不对称」。

**判据**：对某方向按 `[4B 小端长度][载荷]` 切帧，在**首帧或某偏移读到零长、或荒谬大值**，剩余字节无法被消费。此时**不要**立刻断定「该方向没有长度头」「协议不对称」。

**动作**：

```python
import struct
def try_framing(buf, allow_zero=True):
    i, frames = 0, []
    while i + 4 <= len(buf):
        n = struct.unpack_from('<I', buf, i)[0]
        if n == 0 and allow_zero:
            frames.append(b''); i += 4; continue      # 零长心跳帧，放行
        if not (0 < n <= 10_000_000 and i + 4 + n <= len(buf)):
            return None
        frames.append(buf[i+4:i+4+n]); i += 4 + n
    return frames if i == len(buf) else None
```

要点：① 允许零长帧（心跳/保活）；② 流首可能有连续全零段，尝试从多个起始偏移开始切；③ **两个方向都必须断言「消费字节数 == 流长度」**，零剩余才算帧格式正确。

**常见错误结论**：因流首全零心跳让 `0 < n` 判据在首帧失败，据此得出「该方向无长度头、协议不对称」。放行零长帧后，该方向往往与另一方向**完全对称**。要判定协议真不对称，必须先把两个方向都用零剩余断言跑通，再谈差异。

**动作补充**：长度头与载荷可能被拆进**两个独立 TCP 段**（头一个包、体一个包），因此不能按包解析，必须先按 seq 重组再切帧。

**不成立**：允许零长帧且试过多个起始偏移后仍无零剩余，才考虑真的存在第三层结构（如长度含首部自身、命令码、CRC）。

**降级**：无法判断时用工具导出单侧字节流再人工看：`tshark -r x.pcap -q -z follow,tcp,raw,<stream>` 给出无时间戳的纯字节序列，比逐包 hex 更适合找周期性结构。

## 5. 本地化字节对哈希输出：提取与转录防错（复现步骤）

**前置**：命令回显来自本地化（非英文）系统。

**判据**：哈希被输出成若干组空格分隔的 2 位字符（`ab cd ef ...`），而不是连续的定长串。直接 `replace(' ','')` 在其语种/版本下可能残留全角空格或换行。

**动作**：脚本内一次性提取、断言组数与长度、并**由脚本直接 print 最终串**：

```python
import re
toks = re.findall(rb'\b[0-9a-fA-F]{2}\b', md5_line)
hexdigest = b''.join(toks).decode()
assert len(toks) == 16 and len(hexdigest) == 32    # MD5；SHA256 为 32 组 / 64 字符
print(hexdigest)                                   # 唯一真值来源
```

**关键纪律**：**禁止把「空格分隔字节对」人工改写成紧凑串**。手工合并时极易把相邻两个 token 并成一个，漏掉字符，得到长度不足定长的短串——而它看上去完全像一个合法哈希。防错手段三件套：`assert len() == 定长`；三种提取方式交叉验证（`split+join` / `re.findall` / `replace`）；用子串断言证伪（旧错值 `in` 正确值 应为 False）。

**不成立**：若收出的组数不对、或拼接后长度不符，说明抓的是另一行提示（如「哈希计算成功」），回头定位含冒号结尾的那一行。

**降级**：命令行工具不可用时，直接对文件的原始字节算哈希——但要求先能把文件完整取出（从流量导出对象或从磁盘镜像 carve），不要在缺失尾部的情况下算。
