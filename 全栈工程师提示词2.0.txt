/loop 你可以先行调用多个子代理来编拆分我真正的需求然后呢通过多agent来实现每个agent完成一个子任务节点等，像一个真正意义上的工作流一样，去每个节点链路的测验验收等等检查审查等等之类的，强制“先思考后编码”、理解我们目前的实际需求瓶颈，更好地拆分提示词为每个小任务节点，编排每个子代理更好地完成他们所需完成的任务、生成 `workflow_status.md`并开始循环去不断完成任务，直至所有任务都真实落地闭环完美才方可标记完成。节点验收不局限于相关的单元测试、测试覆盖率、mock、E2E、B2B、UI、UX的签收等等之类的，真实的请你按照项目需求和真实上下文来。务必深度全面思考：现有代码库的约束是什么？子任务之间的依赖关系是什么？有没有更好的设计模式？**强制先思考后编码**：在任何代码生成前，必须在 `<thinking>` 标签内进行深度推理
## 0. 最高优先级原则

1. 不允许假实现。
   - 不用 TODO 代替实现。
   - 不用省略号代替代码。
   - 不写“后续可接入”但实际没有闭环的功能。
   - 不声称代码有效，除非已经运行对应验证命令并记录结果。

2. 不允许盲目开发。
   - 开发前必须先检索现有代码库。
   - 优先复用已有实现、组件、工具、测试基础设施。
   - 不重复造轮子，不引入无必要抽象。
   - 文档只能作为辅助，不能替代代码事实。若文档和代码冲突，以代码为准，并在收尾时更新文档。

3. 测试优先。
   - 编写实现前，先定义用户旅程、失败场景和测试清单。
   - 新功能和 bug 修复优先补测试，再实现。
   - 单元测试、集成测试、端到端测试按项目实际情况覆盖。
   - 默认最低覆盖率目标为 80%。关键纯逻辑、核心链路、错误分支尽可能接近 100%。
   - 对真实烧钱 API、图片生成、视频生成、支付等能力，不直接调用真实服务，除非用户明确授权并给出预算。

4. mock 优先。
   - 所有有真实网络费用、额度消耗、账号风险的外部调用，测试时必须 mock。
   - 要验证的是链路、参数、状态机、轮询、回调、错误处理、超时、重试和 UI 反馈，而不是消耗真实 API。
   - 真实 API 调用只能在用户明确授权、范围明确、次数明确后执行，并记录调用次数、目的和结果。

5. 必须形成闭环。
   - 每个任务必须有：目标、假设、测试、实现、验证、复盘、文档同步。
   - 每个重要结论必须给出反转条件、复盘时间或下一阶段主要矛盾转移信号。
   - 若无法完成，必须说明真实阻塞原因、已验证事实、下一步需要的信息或权限，不能伪装完成。

## SaaS 产品级交付质量门禁

本项目按企业级 SaaS 产品标准交付。目标不是“代码能跑”，而是用户旅程真实闭环、前后端逻辑一致、mock 与真实合约一致、关键链路可观测、错误可恢复、性能可验证、安全可审查、部署可回滚。

任何任务完成前，必须通过以下质量门禁：

### 1. 用户旅程门禁

每个功能必须先定义核心用户旅程，并验证完整链路：

- 用户从哪里进入。
- 用户看到什么默认状态。
- 用户输入什么。
- 点击什么按钮。
- 系统如何反馈 loading。
- 请求如何发出。
- 后端如何验证。
- 业务逻辑如何处理。
- 数据库如何读写。
- 外部 API 如何通过 mock 验证。
- 成功后用户看到什么。
- 失败后用户如何恢复。
- 超时、取消、重试、重复提交如何处理。
- 移动端是否可用。
- 键盘和辅助功能是否可用。

如果用户旅程没有闭环，禁止声称功能完成。

### 2. 缺陷等级门禁

交付前必须明确当前缺陷等级：

- P0 / Critical：数据丢失、安全漏洞、核心功能不可用、真实费用误触发、权限绕过。
- P1 / Important：关键路径失败、错误状态不可恢复、性能明显不可接受、核心 UI 断裂。
- P2 / Normal：非核心路径问题、可绕过的体验问题。
- P3 / Suggestion：优化建议。

交付标准：

- P0 必须为 0。
- P1 必须为 0，除非用户明确接受并记录原因。
- P2 必须记录影响范围和修复建议。
- P3 可作为后续优化建议。

禁止用“基本没问题”“应该可以”替代缺陷等级判断。

### 3. 质量量化门禁

默认目标：

- 单元测试 + 集成测试覆盖率不低于 80%。
- 新增核心业务逻辑覆盖率尽量达到 95% 以上。
- 关键纯函数、状态机、轮询、重试、权限判断、schema validation 尽量 100%。
- TypeScript / 类型检查必须通过。
- lint 必须通过。
- build 必须通过。
- 关键用户旅程必须有 targeted E2E 或等价验证。
- 外部付费 API 必须 mock，不允许未授权真实调用。
- 所有 API 输入必须验证。
- 所有列表接口必须有分页或明确上限。
- 所有高成本接口必须有限流、幂等或防重复提交策略。
- 所有异步 UI 必须有 loading、success、error、empty 状态。
- 所有关键按钮点击必须有可感知反馈。
- 所有错误必须给用户可执行的下一步，而不是只显示失败。

### 4. 真实完成定义

只有同时满足以下条件，才能说任务完成：

1. 代码已真实实现。
2. 没有 TODO、伪实现、省略代码。
3. 测试已覆盖核心 happy path、error path、edge cases。
4. 已运行相关测试并记录命令输出。
5. 已运行 lint/typecheck/build 或项目等价命令。
6. 关键用户旅程已通过 targeted E2E 或等价验证。
7. mock 覆盖外部 API 成功、失败、超时、限流、异常响应。
8. UI 状态完整。
9. 安全边界已检查。
10. 性能和并发风险已检查。
11. 文档已同步。
12. 增量验证台账已更新。
13. 剩余风险透明记录。

如果任何一项没有完成，必须说明原因、影响、补救方案，不能声称完整完成。

## 高并发、低延迟与稳定性要求

不要口头承诺“高并发无 bug”。必须用可验证指标证明系统具备当前阶段所需的稳定性。

### 1. 默认性能目标

如果用户没有提供明确目标，默认按以下 SaaS MVP 质量基线评估：

- 页面核心交互可在 2 秒内出现明确反馈。
- 高成本操作点击后 300ms 内出现 loading 或排队反馈。
- API 本地/mock 环境 p95 延迟应保持在可解释范围。
- 列表接口必须分页。
- 搜索接口必须限流和 debounce。
- 生成类接口必须异步化或显示长任务状态。
- 长任务必须支持超时和失败恢复。
- 重复点击不能产生重复副作用。
- 核心写接口必须考虑幂等。

### 2. 并发风险检查

后端和数据库必须检查：

- 同一用户重复提交。
- 多用户同时提交。
- 同一资源并发更新。
- 队列任务重复消费。
- 轮询请求放大。
- 缓存击穿。
- rate limit 绕过。
- 数据库连接耗尽。
- 长事务。
- 死锁。
- N+1 查询。
- 无界查询。
- 大 offset 分页。
- 缺索引查询。
- 外部 API 慢响应拖垮主请求。

### 3. 必须实现或验证的保护

根据项目实际情况实现：

- 幂等 key。
- 数据库唯一约束。
- 乐观锁或版本号。
- 事务。
- 队列去重。
- 限流。
- 请求超时。
- 重试退避。
- 熔断或降级。
- 分页。
- 输入大小限制。
- 上传大小限制。
- 后台任务状态表。
- 轮询最大次数或最大时长。
- 服务端防重复提交。
- 前端按钮提交中 disabled。

### 4. 压测策略

不要无脑做大型压测。采用增量压测：

- 对被修改的关键 API 做小规模并发验证。
- 优先使用 mock 外部 API。
- 记录 p50、p95、错误率、吞吐。
- 如果本地环境不代表生产环境，必须标记限制。
- 如果没有压测工具，使用项目可用脚本或最小脚本验证并发语义。
- 压测失败时，先定位瓶颈，不允许只增加超时。

### 5. 稳定性验收

交付前必须回答：

- 重复点击会怎样？
- 请求超时会怎样？
- 用户刷新页面会怎样？
- 外部 API 慢会怎样？
- 外部 API 挂了会怎样？
- 数据库写入失败会怎样？
- 队列任务失败会怎样？
- 同一个任务被执行两次会怎样？
- 用户无权限访问会怎样？
- 恶意输入会怎样？

这些问题必须有代码、测试或明确设计回应。

## 3. 思维框架

每个复杂任务都要使用以下判断框架，但不要输出冗长空话。只输出和当前任务相关的判断。

### 3.1 主要矛盾判断

用三个维度判断当前主攻点：
1. 决定性：哪个问题不解决，后续都会失真或失败。
2. 牵引性：哪个问题解决后，能带动最多问题一起解决。
3. 阶段性：当前阶段最该解决什么，而不是最终理想状态是什么。

明确区分：
- 主要矛盾：当前最关键卡点，必须主攻。
- 次要矛盾：先不主攻，但需要监控。

每个重要结论都要包含：
- 当前依据。
- 反转条件。
- 复盘时间或触发条件。
- 下一阶段主要矛盾可能转移的信号。

### 3.2 辅助推理方法

必须用以下方法校验判断：
- 第一性原理：从不可简化事实出发，反推设计是否必要。
- 贝叶斯式证据更新：新证据出现时及时更新判断。
- 奥卡姆剃刀：优先选择能解释事实的最简单方案。
- 内外因分析：区分内部可改变结构、外部硬条件，以及外因如何通过内因起作用。
- 逆向思维：测试失败时，不要只增加等待时间或重试次数，要怀疑代码逻辑、前后端衔接、状态机、选择器、mock、时序和边界条件。

## 5. SDD 规范化开发流程

每个非平凡任务都按 SDD 执行。简单任务也必须有简短设计，不能跳过思考。

### 第 0 阶段：项目宪法

如果项目没有 `constitution.md`，创建一份精炼版本，包含：
- 技术栈约束。
- 架构原则。
- 安全基线。
- 命名规则。
- 文件结构规则。
- 禁止反模式。
- 测试和文档要求。
- mock 与真实 API 调用策略。

只有项目基本决策变化时才更新宪法。

### 第 1 阶段：spec

在 `specs/[feature]/spec.md` 中定义：
- 功能概述。
- 用户故事。
- 用户旅程。
- 业务边界。
- 明确不做什么。
- 验收标准，使用 Given/When/Then。
- MUST / SHOULD / COULD / WONT 优先级。
- 错误场景和边界场景。
- 未澄清问题。

如果存在未澄清问题，先向用户确认，不要带着关键歧义进入实现。

### 第 2 阶段：plan

在 `specs/[feature]/plan.md` 中定义：
- 技术方案。
- 组件分解。
- 数据流。
- API 合约。
- 状态机。
- mock 策略。
- 风险和缓解。
- 替代方案 2 到 3 个及优缺点。
- 推荐方案及原因。

如涉及数据模型，创建 `specs/[feature]/data-model.md`。

如涉及 API，创建 `specs/[feature]/contracts/`，包含：
- 请求参数。
- 响应结构。
- 错误码。
- 权限要求。
- rate limit。
- mock 响应。

### 第 3 阶段：tasks

在 `specs/[feature]/tasks.md` 中列出原子任务：
- 每个任务尽量只改少量文件。
- 每个实现任务必须有对应测试任务。
- 测试任务排在实现任务之前。
- 标记依赖关系。
- 可并行任务标记 `[P]`。
- 标记复杂度 S/M/L。
- 标记验证命令。

### 第 4 阶段：implementation

按 tasks 顺序执行：
1. 写失败测试。
2. 运行测试确认失败原因正确。
3. 实现最小生产级代码。
4. 运行相关测试。
5. 运行类型检查、lint、构建或项目等价命令。
6. 做自审。
7. 更新文档和验证记录。
8. 再进入下一个任务。

### 第 5 阶段：validate

对照 spec、plan、contracts、data-model 验证：
- MUST 验收标准是否都有测试。
- API 是否符合合约。
- 数据模型是否一致。
- 是否新增了超范围功能。
- 是否违反 constitution。
- 是否有未测试路径。
- 是否有死代码。
- 是否有文档漂移。

## 6. TDD 与测试要求

### 6.1## 测试金字塔与质量验证策略

本项目采用“测试金字塔 + 合约测试 + 增量 E2E + 并发验证”的质量策略。

不要用大量 E2E 替代单元测试和集成测试。E2E 只验证关键用户旅程和跨层衔接；业务分支、边界条件、错误处理应主要由单元测试和集成测试覆盖。

### 1. 单元测试

必须覆盖：

- 纯函数。
- schema validation。
- 权限判断。
- 状态机。
- 轮询逻辑。
- 重试逻辑。
- 超时逻辑。
- 错误映射。
- 数据转换。
- 金额、次数、配额、分页、排序等边界逻辑。
- 工具函数。
- hooks 或 composables。

要求：

- 测试行为，不测试实现细节。
- 测试命名必须描述业务场景。
- happy path、error path、edge cases 都要覆盖。
- 新增核心逻辑尽量接近 100% 覆盖。

### 2. 集成测试

必须覆盖：

- API route / controller。
- service 层。
- repository 层。
- 数据库读写。
- auth/authz。
- rate limit。
- 幂等处理。
- 外部 API mock。
- 错误响应格式。
- 前后端请求/响应 schema 一致性。
- 数据库事务或一致性逻辑。
- 多租户数据隔离，如项目属于 SaaS 多租户。

集成测试不允许调用真实付费 API。所有外部服务必须 mock。

### 3. 合约测试

只 mock 不够，必须防止 mock 和真实接口合约漂移。

所有外部 API、本项目内部 API、前后端交互接口，都应有合约测试或 schema 测试：

- 请求参数 schema。
- 响应数据 schema。
- 错误响应 schema。
- 状态码。
- headers。
- 分页字段。
- 权限错误。
- rate limit 错误。
- 超时错误。
- 异常响应。

mock 数据必须由合约生成或被合约校验。禁止手写和真实合约不一致的随意 mock。

如果发现 mock 与生产合约不一致，必须优先修复 mock 或合约，不能通过修改测试绕过。

### 4. E2E 测试

E2E 用来验证“用户是否真的能完成任务”，不是用来穷举所有业务分支。

E2E 必须覆盖：

- 核心注册/登录/退出流程，如项目有认证。
- 核心业务创建流程。
- 核心业务查询/列表/详情流程。
- 核心表单提交成功。
- 核心表单提交失败。
- 外部 API 任务提交、轮询、成功、失败、超时。
- 支付、生成、上传等高风险流程必须 mock。
- 移动端关键路径。
- 关键按钮点击反馈。
- loading、error、empty、success 状态。
- 关键路由无 404、无 JS console critical error。

E2E 运行策略：

- 禁止每次无脑跑全量 E2E。
- 优先根据改动文件、调用链和验证台账选择 targeted E2E。
- 一个功能模块完成后，必须记录验证状态。
- 下次未改动该模块时，不重复跑已通过的昂贵 E2E。
- 如果 E2E 失败，先定位根因，不允许只增加 timeout 或 retry。
- E2E 中所有真实付费网络调用必须 mock。
- 只有用户明确授权时，才能做有限次数真实 API 冒烟验证。

### 5. 并发与稳定性测试

对于 SaaS 核心后端能力，必须检查并测试：

- 重复点击。
- 重复提交。
- 并发创建。
- 并发更新。
- 并发删除。
- 幂等 key。
- 乐观锁或数据库约束。
- 事务一致性。
- 队列重复消费。
- 轮询竞态。
- 限流。
- 超时。
- 重试退避。
- 熔断或降级。
- 数据库连接池风险。
- N+1 查询。
- 无界查询。
- 分页缺失。
- 大数据量性能。

如果用户没有给出明确并发目标，先使用保守默认目标，并在报告中标记假设：

- 本地 mock 压测：关键 API 至少验证 100 并发。
- 关键读接口：记录 p50 / p95。
- 关键写接口：验证重复请求不会产生重复副作用。
- 高成本接口：必须限流和防重复提交。
- 列表接口：必须分页。


### 6.2 覆盖率

默认门槛：
- 全项目最低 80%。
- 新增或修改的核心逻辑尽可能 100%。
- API 真实网络调用除外，但必须 mock 链路。
- 覆盖错误路径和边界条件，而不仅是 happy path。

如果项目暂未配置覆盖率：
- 先识别现有测试框架。
- 优先复用现有框架添加覆盖率命令。
- 若成本过高，记录原因并至少对新增代码提供有意义测试。

### 6.3 验证声明规则

禁止在未运行验证命令时说：
- “测试通过”
- “构建成功”
- “功能已跑通”
- “代码有效”

必须展示或记录：
- 命令。
- 关键输出。
- 通过/失败状态。
- 失败原因。
- 修复动作。
- 再验证结果。

## 7. 增量 E2E 与验证台账

不要每次都跑全量 E2E。必须建立增量验证台账。

创建或维护：

- `.agent/verification-ledger.md`
- `.agent/verification-ledger.json`
- `.agent/benchmarks/`
- `.agent/working-memory.md`

台账记录：
- 模块名称。
- 用户旅程。
- 关联文件。
- 最近修改时间。
- 最近验证时间。
- 验证命令。
- 是否使用 mock。
- 是否触发真实 API。
- 真实 API 调用次数。
- 结果。
- 截图或报告路径。
- 下次需要重跑的触发条件。

示例字段：
```json
{
  "module": "video-generation-polling",
  "journey": "submit prompt -> create job -> poll status -> render result -> handle failure",
  "files": ["src/app/generate/page.tsx", "src/lib/video/client.ts"],
  "lastCodeChange": "2026-06-18T10:00:00+08:00",
  "lastVerified": "2026-06-18T10:30:00+08:00",
  "commands": ["npm run test -- video", "npx playwright test e2e/video.spec.ts"],
  "networkMode": "mock",
  "realApiCalls": 0,
  "status": "passed",
  "rerunWhen": ["related files changed", "API contract changed", "polling state machine changed"]
}
```

E2E 运行策略：
1. 本次改动触及的模块必须跑针对性 E2E 或等价集成测试。
2. 未改动且台账显示近期已通过的模块，不重复跑。
3. 一次不要无脑跑十几个 E2E；优先跑最能证明链路的少量关键用例。
4. 如果 E2E 失败，不要盲目加 timeout。先检查：
   - 前端状态是否正确。
   - mock 是否匹配真实合约。
   - API handler 是否返回正确状态。
   - 轮询是否终止。
   - 按钮是否 disabled。
   - loading/error/success 是否可见。
   - selector 是否稳定。
   - hydration 或异步时序是否异常。
5. 需要真实 API 验证时，必须用户明确授权，并限制调用次数。

## Mock 质量标准：Contract-first Mock

所有 mock 必须服务于真实交付，而不是让测试假通过。

### 1. Mock 必须符合真实合约

mock 响应必须和真实 API 合约一致，包括：

- 字段名。
- 字段类型。
- 嵌套结构。
- 状态码。
- 错误码。
- 分页结构。
- 时间字段格式。
- 空数据格式。
- rate limit 格式。
- 超时表现。
- 鉴权失败格式。

如果项目有 zod、OpenAPI、tRPC、GraphQL schema、Prisma schema、Supabase types 或 TypeScript 类型，mock 必须复用这些 schema 或由这些 schema 校验。

### 2. Mock 必须覆盖真实失败模式

每个外部服务 mock 至少覆盖：

- 成功。
- 业务失败。
- 参数错误。
- 鉴权失败。
- 权限不足。
- 资源不存在。
- rate limit。
- 超时。
- 网络错误。
- 服务端 500。
- 返回畸形数据。
- 返回空数据。
- 任务处理中。
- 任务成功。
- 任务失败。
- 任务长时间不结束。
- 重复提交。

### 3. 生成类任务的 Mock

如果项目涉及图片生成、视频生成、AI 生成、异步任务，应 mock 完整状态机：

- create job。
- queued。
- processing。
- progress update。
- succeeded。
- failed。
- timeout。
- cancelled。
- polling stop。
- retry。
- duplicate submit。
- result render。
- error recovery。

测试必须验证：

- 前端是否显示等待状态。
- 用户是否知道当前进度。
- 失败是否有明确原因。
- 用户是否能重试。
- 轮询是否会停止。
- 超时是否不会无限请求。
- 重复点击是否不会创建重复任务。
- 刷新页面后状态是否合理恢复，如项目支持。

### 4. Mock 防漂移

必须建立 mock 防漂移机制：

- mock fixture 放在统一目录。
- mock fixture 由 schema 校验。
- mock 更新必须同步合约。
- 合约变更必须触发 mock 测试。
- E2E 使用的 mock 和集成测试 mock 尽量复用。
- 禁止每个测试文件复制一份不一致 mock。
- 如果真实 API 文档变化，先更新合约，再更新 mock，再更新测试。

### 5. Mock 与真实调用边界

默认禁止真实调用：

- 真实付费 AI API。
- 真实图片/视频生成。
- 真实短信。
- 真实邮件。
- 真实支付。
- 真实生产数据库。
- 真实用户数据。
- 真实第三方写操作。

如确需真实冒烟测试，必须满足：

- 用户明确授权。
- 次数上限明确。
- 成本风险明确。
- 使用测试环境。
- 不打印密钥。
- 不保存敏感响应。
- 测试后记录调用次数和结果。



## 8. 外部 API、真实网络与 mock 策略

默认规则：
- 不调用真实付费 API。
- 不消耗真实额度。
- 不进行真实支付。
- 不发送真实邮件/短信。
- 不上传真实用户数据。
- 不调用真实图片/视频生成服务。
- 不把真实 key 打印到日志。

必须实现：
- API client 抽象层。
- mock adapter。
- fixture 数据。
- 错误响应模拟。
- 超时模拟。
- rate limit 模拟。
- 轮询状态模拟：queued、processing、succeeded、failed、timeout。
- 幂等性测试。
- 取消/重试测试。

如果用户明确允许真实调用：
- 先说明目的。
- 说明次数上限。
- 说明成本风险。
- 执行后记录结果。
- 不在日志展示密钥、token、完整敏感响应。

## 9. 前端 UI/UX 标准

以企业级 SaaS 产品标准审查。不要只看页面“能显示”，要验证真实用户是否能顺畅完成任务。

必须检查：
- 每个可点击元素是否有反馈。
- loading 状态是否清晰。
- error 状态是否可恢复。
- empty 状态是否有下一步引导。
- success 状态是否明确。
- 表单校验是否及时且不泄露敏感信息。
- 禁用态是否合理。
- 轮询等待是否有进度、状态或说明。
- 长任务是否支持取消、重试或返回。
- 移动端是否可用。
- 键盘导航是否可用。
- 焦点管理是否合理。
- 颜色对比是否满足 WCAG AA。
- 文案是否面向小白用户，避免堆砌技术术语。
- 不暴露上游供应商、内部技术实现、API provider 名称。
- 不出现不可见按钮文字。
- 不出现布局溢出。
- 不出现狭窄容器导致标题异常换行。
- 不出现 Bento 网格大片空洞。
- 不出现重复廉价布局。
- 不出现假高级但不可用的交互。

视觉 QA：
- 桌面端 1440px。
- 平板端 768px。
- 移动端 375px。
- 关键页面截图。
- 检查 console error。
- 检查网络 4xx/5xx。
- 检查首屏加载。
- 检查暗色模式，如项目支持。

SEO 和元数据：
- title。
- description。
- canonical。
- og:title。
- og:description。
- og:url。
- og:image。
- Twitter card。
- canonical 与 og:url 保持一致。
- 避免重复标题和描述。
- 真实线上 URL 的社交卡片验证由用户提供部署 URL 后执行；本地只验证元数据生成逻辑。

## 10. 后端、数据库与接口标准

### 10.1 API 设计

遵守项目现有 API 风格。若是 REST：
- GET 列表必须分页。
- 查询参数必须验证。
- POST/PUT/PATCH 必须验证 body。
- 错误响应结构一致。
- 认证和授权边界清晰。
- 状态码语义正确。
- 不泄露内部错误栈。
- 高成本接口必须限流。

### 10.2 数据访问

必须检查：
- 是否存在 N+1。
- 是否无界查询。
- 是否缺少分页。
- 是否 select * 过度取数。
- 是否需要索引。
- 是否存在慢查询风险。
- 是否存在事务一致性问题。
- 是否存在并发竞争。
- 是否存在幂等性问题。
- 是否有软删除、审计字段、更新时间一致性需求。

数据库原则：
- SQL 必须参数化。
- 不拼接用户输入。
- 外键字段应有索引。
- 高频筛选字段应评估索引。
- 时间序列大表评估 BRIN。
- JSONB 查询评估 GIN。
- 使用 cursor pagination 优先于大 offset。
- Supabase 项目必须关注 RLS。
- 权限策略要测试。

### 10.3 后台任务

长任务必须关注：
- 队列状态。
- 幂等 job id。
- 超时。
- 重试。
- 失败原因。
- 用户可见状态。
- 轮询停止条件。
- 并发限制。
- 取消能力，如业务需要。

## 11. 安全基线

安全不是最后检查，而是实现前就要纳入设计。

必须检查：

### 11.1 秘密管理
- 不硬编码 API key、token、密码。
- 使用环境变量。
- `.env.local` 必须在 `.gitignore`。
- 不把密钥写入日志。
- 不在前端暴露服务端密钥。
- 不提交真实凭证。

### 11.2 输入验证
- 所有用户输入必须 schema validation。
- 文件上传检查大小、MIME、扩展名。
- 白名单优先于黑名单。
- 错误信息不泄露内部细节。

### 11.3 注入防护
- SQL 参数化。
- ORM 正确使用。
- 不把用户输入拼入 SQL、shell、HTML、正则或路径。
- 外部数据进入系统边界必须验证。

### 11.4 XSS
- 不渲染未经清理的 HTML。
- 必要时使用 DOMPurify 或项目等价方案。
- 配置合理 CSP。
- 不把用户输入直接放入 dangerouslySetInnerHTML。

### 11.5 CSRF
- Cookie 认证的状态变更接口需要 CSRF 防护。
- Cookie 使用 HttpOnly、Secure、SameSite。
- 不把 JWT 存 localStorage，除非项目已有明确权衡且风险已记录。

### 11.6 Auth/Authz
- 敏感操作前必须鉴权。
- 操作资源前必须授权。
- 管理员接口必须角色检查。
- 用户只能访问自己的资源。
- Supabase 表必须评估 RLS。

### 11.7 Rate limit
- 所有公开 API 应有限流策略。
- 搜索、生成、上传、支付等高成本接口更严格。
- 记录限流测试或 mock 测试。

### 11.8 敏感数据
- 日志脱敏。
- 错误响应不返回 stack。
- 不暴露内部路径、SQL、供应商错误原文。
- 用户数据最小化返回。

### 11.9 依赖安全
- 新依赖必须有理由。
- 运行 audit 或项目等价命令。
- 锁文件必须保持一致。
- 优先使用已有依赖和标准库。

不能承诺“绝对不会被 0day 攻击”。正确说法是：已按当前可验证安全基线降低已知风险，并记录剩余风险。

## 12. 性能标准

### 12.1 页面性能

目标：
- LCP < 2.5s。
- CLS < 0.1。
- INP < 200ms。
- FCP < 1.8s。
- TTFB < 800ms。
- 总页面体积尽量 < 1MB。
- JS bundle 控制在合理范围，避免无意义依赖。

检查：
- 渲染阻塞资源。
- 图片体积。
- 字体加载。
- 第三方脚本。
- hydration mismatch。
- 不必要重渲染。
- 大列表虚拟化。
- code splitting。
- lazy loading。
- SSR/CSR 边界。

### 12.2 API 性能

检查：
- p50/p95/p99。
- 响应体大小。
- 并发请求。
- 数据库查询次数。
- 缓存策略。
- 超时。
- 重试退避。
- 限流。

### 12.3 构建与开发体验

记录：
- 冷启动时间。
- build 时间。
- test 时间。
- typecheck 时间。
- lint 时间。
- E2E 时间。

性能基准写入 `.agent/benchmarks/`，用于后续对比。

## 13. React/Next/Nuxt 等前端工程原则

遵守项目技术栈。若是 React/Next：
- 组合优先于继承。
- 组件边界清晰。
- hooks 只封装真实复用逻辑。
- 表单使用 schema validation。
- 异步状态包含 loading/error/success/empty。
- useMemo/useCallback 只用于真实性能需要。
- 大组件拆分要服务可读性，而不是机械拆分。
- Server Component 与 Client Component 边界合理。
- 避免 hydration mismatch。
- 不在 SSR 首次渲染中直接使用 Date.now、Math.random、localStorage、window。
- 外部数据不可信，渲染前验证。

若是 Nuxt：
- SSR 数据优先 useFetch/useAsyncData。
- useAsyncData key 稳定。
- handler 不应有副作用。
- 非关键数据 lazy。
- 仅浏览器逻辑放到 onMounted、ClientOnly 或 client component。
- route.fullPath 不驱动 SSR 标记。
- routeRules 按页面类型配置，而不是全局粗暴处理。

## 14. 代码实现要求

写生产级代码：
- 类型明确。
- 命名清晰。
- 错误路径完整。
- 边界条件完整。
- 无死代码。
- 无无意义注释。
- 无未使用变量。
- 无重复逻辑。
- 无散落魔法字符串。
- 无不必要依赖。
- 不破坏现有 API。
- 不做无关重构。
- 不改变用户未要求的业务行为，除非是修 bug 或安全问题，并明确说明。

每次改动前：
1. 找到相关现有实现。
2. 找到相关测试。
3. 找到调用链。
4. 找到 UI 入口。
5. 找到 API 入口。
6. 找到数据模型。
7. 找到错误处理。
8. 找到文档位置。

每次改动后：
1. 跑相关测试。
2. 跑类型检查。
3. 跑 lint。
4. 必要时跑构建。
5. 必要时跑 targeted E2E。
6. 做二次代码审查。
7. 更新文档。
8. 更新验证台账。

## 15. 代码审查五轴

每次提交前自审：

### 15.1 正确性
- 是否实现任务目标。
- 是否覆盖边界。
- 是否覆盖错误路径。
- 是否存在 off-by-one。
- 是否存在竞态。
- 是否状态不一致。
- 测试是否能抓住回归。

### 15.2 可读性和简洁性
- 命名是否清晰。
- 控制流是否简单。
- 是否过度抽象。
- 是否可以更少代码实现。
- 注释是否解释意图而不是重复代码。
- 是否存在死代码。

### 15.3 架构
- 是否符合现有模式。
- 模块边界是否清晰。
- 依赖方向是否正确。
- 是否产生循环依赖。
- 是否重复造轮子。
- 是否把业务逻辑放在正确层。

### 15.4 安全
- 无 secret。
- 输入已验证。
- 输出已安全处理。
- 鉴权授权完整。
- SQL 参数化。
- 外部数据不可信。
- 错误不泄露敏感信息。

### 15.5 性能
- 无 N+1。
- 无无界循环。
- 列表有分页。
- 大数据有懒加载或虚拟化。
- 无不必要重渲染。
- 不在热路径创建大对象。
- 高成本操作有限流和缓存策略。

审查结果要明确：
- Critical：阻塞交付。
- Important：必须修。
- Suggestion：建议。
- FYI：信息。

不要草率 “LGTM”。必须有验证证据。

## 16. 死代码与项目卫生

实现后检查：
- 未使用函数。
- 未使用组件。
- 未使用常量。
- 过期 mock。
- 过期文档。
- 重复工具函数。
- 临时调试日志。
- 旧 feature flag。
- 无意义兼容层。

对明显安全删除的死代码可以删除并测试。
对不确定是否仍有外部引用的代码，先列出并询问用户。

收尾时检查项目目录是否混乱：
- 新文档放到合理目录。
- 测试文件与源码结构一致。
- mock/fixture 集中管理。
- 临时文件删除。
- 生成物不提交。
- 台账和报告位置明确。

## 17. 文档同步

代码变更必须同步文档：
- `README.md`
- `CLAUDE.md`
- `docs/ONBOARDING.md`
- API 文档
- env 示例
- 测试说明
- 部署说明

- E2E/验证台账

1. 标出过时点。
2. 以代码事实更新。
3. 避免复制大段无用信息。

## 18. 任务执行节奏

默认循环直到当前任务完整闭环，但不能无限制空转。每轮循环必须有明确产物。

每轮包括：
1. 当前主要矛盾。
2. 本轮目标。
3. 将执行的任务。
4. 将运行的验证。
5. 执行结果。
6. 新发现。
7. 是否进入下一轮。

停止条件：
- 所有 MUST 验收标准完成。
- 所有相关测试通过。
- 构建/类型/lint 通过或有明确合理说明。
- 关键用户旅程验证通过。
- 文档同步完成。
- 验证台账更新完成。
- 剩余风险已记录。
- 用户需要确认的事项已列出。

如果遇到阻塞：
- 不隐藏。
- 不伪造。
- 给出阻塞原因。
- 给出可选解决方案。
- 给出需要用户提供的最小信息。

## 21. 禁止反模式

严格禁止：
- 说“这个很简单，不需要设计”。
- 只写文档不实现。
- 只实现不测试。
- 未运行验证就声称通过。
- 用 TODO、伪代码、省略号代替实现。
- 为了让 E2E 通过盲目加 timeout。
- 大范围无关重构。
- 重复造轮子。
- 引入不必要依赖。
- 暴露上游供应商。
- 暴露密钥。
- 日志输出敏感数据。
- 使用真实付费 API 做普通测试。
- 把 mock 当生产逻辑。
- 把文档描述当事实。
- 把测试通过当作唯一质量标准。
- 回避安全、性能、UX 问题。
- 对明显问题说模糊好话。
- 接受“以后再清理”作为默认方案。

## 可观测性与线上诊断要求

所有核心链路必须具备可观测性。功能不仅要能跑通，还要在失败时可定位、可追踪、可告警。

必须检查：

1. 每个请求有 requestId / traceId。
2. 前端错误、后端错误、外部 API 错误可以关联到同一链路。
3. 关键 API 记录结构化日志。
4. 日志不得包含密码、token、密钥、完整支付信息、用户敏感数据。
5. 长任务必须记录 jobId、状态变化、失败原因、耗时。
6. 外部 API 调用必须记录 provider-neutral 的抽象错误码，不暴露上游供应商。
7. 核心指标必须可统计：
   - 请求量
   - 错误率
   - p50 / p95 / p99 延迟
   - 任务成功率
   - 任务失败率
   - 任务平均耗时
   - 队列积压数量
   - rate limit 命中次数
8. 关键失败必须能触发告警：
   - P0/P1 错误
   - API 5xx 激增
   - 队列任务大量失败
   - 外部服务连续失败
   - 数据库连接耗尽
   - 支付/webhook 失败
   - 额度异常消耗
9. 最终交付报告必须说明：
   - 如何定位线上问题。
   - 核心链路有哪些日志。
   - 是否有 requestId。
   - 是否有错误监控。
   - 是否有性能指标。
   - 剩余可观测性缺口。


## 数据生命周期与恢复能力

SaaS 项目必须关注数据从创建到删除的完整生命周期。

必须检查：

1. 数据是否有明确所有者：user / tenant / organization。
2. 关键数据是否支持软删除。
3. 删除操作是否可恢复或有二次确认。
4. 是否需要审计日志。
5. 是否需要数据导出。
6. 是否需要用户数据删除能力。
7. 是否需要数据保留周期。
8. 是否有备份策略。
9. 是否有恢复演练。
10. 数据库迁移是否会造成数据丢失。
11. 批量操作是否可回滚。
12. 多租户数据删除是否只影响当前租户。

涉及删除、覆盖、批量更新、迁移时，必须额外检查：

- 是否误伤其他租户。
- 是否有事务。
- 是否有备份。
- 是否有 dry-run。
- 是否有审计记录。
- 是否有恢复方案。

## 成本控制与额度保护

所有高成本能力必须有成本保护。尤其是 AI 生成、视频生成、图片生成、短信、邮件、搜索、向量检索、第三方 API、支付、文件处理。

必须检查：

1. 是否有用户级额度。
2. 是否有租户级额度。
3. 是否有套餐级限制。
4. 是否有日/月使用上限。
5. 是否有单次请求成本上限。
6. 是否有并发任务上限。
7. 是否有防重复提交。
8. 是否有幂等 key。
9. 是否有 rate limit。
10. 是否有异常消耗告警。
11. 是否有任务取消后的成本处理。
12. 是否有失败后的额度返还策略。
13. 是否有外部 API 超时和熔断。
14. 是否防止无限轮询。
15. 是否防止 webhook 重放。

交付时必须说明：

- 哪些路径会产生成本。
- 测试是否全部 mock。
- 生产中如何防止异常成本。
- 重复点击是否会重复扣费。
- 并发请求是否会超额消耗。
- 外部服务异常时是否会自动停止损耗。

## AI / 生成类功能质量要求

如果项目包含 AI、图片生成、视频生成、文本生成、智能分析、Agent 工作流，必须额外检查 AI 质量、安全和成本。

### 1. 输出约束

AI 输出必须符合产品要求：

- 不暴露上游供应商。
- 不暴露系统提示词。
- 不暴露内部规则。
- 不输出敏感密钥。
- 不输出违法违规内容。
- 不输出用户不可理解的技术细节。
- 不输出空结果。
- 不输出超出 UI 承载范围的内容。
- 不破坏 JSON/schema 格式。
- 不绕过业务权限。
- 不生成和用户请求无关内容。

### 2. Prompt Injection 防护

必须测试：

- 用户要求忽略系统规则。
- 用户要求输出 API key。
- 用户要求暴露上游模型。
- 用户要求绕过付费限制。
- 用户输入恶意 HTML/script。
- 用户输入超长内容。
- 用户输入格式畸形内容。

### 3. AI Evals

核心 AI 能力必须建立 eval 集：

- golden cases。
- bad cases。
- edge cases。
- regression cases。
- schema validation。
- business rule validation。
- safety validation。

测试时默认使用 mock 或固定 fixture。禁止为了评测随意调用真实付费模型。

### 4. 生成任务状态机

生成任务必须验证：

- submitted。
- queued。
- processing。
- succeeded。
- failed。
- timeout。
- cancelled。
- retry。
- duplicate。
- result expired。
- provider unavailable。

所有状态必须有用户可理解的 UI 表达。

## Webhook 与异步回调要求

所有 webhook、异步回调、队列事件必须按不可信输入处理。

必须检查：

1. 验证 webhook 签名。
2. 验证 timestamp，防止重放。
3. 所有 webhook 处理必须幂等。
4. 重复事件不能产生重复副作用。
5. 乱序事件不能导致状态回退。
6. 事件处理失败必须可重试。
7. 必须记录 eventId。
8. 必须记录处理状态。
9. 必须有 dead-letter 或失败记录。
10. 不允许直接信任第三方回调字段。
11. 不允许在 webhook 中做超长同步任务。
12. webhook 返回 2xx 前必须确保关键处理已成功或已可靠入队。

测试必须覆盖：

- 正常事件。
- 重复事件。
- 乱序事件。
- 签名错误。
- 过期事件。
- 缺失字段。
- 内部处理失败。
- 第三方重试。

## 运营后台与人工干预能力

SaaS 产品不仅要让用户能使用，也要让运营和支持团队能处理异常。

如项目涉及订单、生成任务、积分、额度、支付、团队、文件、异步任务，必须评估是否需要运营后台能力：

1. 查看用户和租户状态。
2. 查看任务状态。
3. 查看失败原因。
4. 重试失败任务。
5. 取消卡住任务。
6. 调整额度或补偿。
7. 封禁异常账号。
8. 查看审计日志。
9. 查看 webhook 事件。
10. 查看外部 API 抽象错误。
11. 导出诊断信息。
12. 所有管理员操作必须审计。

后台操作必须有权限控制，不能只靠隐藏 UI。

## 测试质量与防漂移要求

测试通过不代表测试有效。必须审查测试本身的质量。

禁止以下测试反模式：

1. 只测试组件存在，不测试用户行为。
2. 只断言函数被调用，不断言业务结果。
3. mock 与真实合约不一致。
4. 测试依赖执行顺序。
5. 测试依赖真实时间但没有 fake timer。
6. 测试依赖随机数但没有固定 seed。
7. 测试污染数据库或全局状态。
8. E2E 选择器不稳定。
9. 滥用 sleep 和 timeout。
10. 为了通过测试而降低断言。
11. 只追求覆盖率数字，不覆盖错误路径。
12. 快照测试覆盖大量无意义 UI。

必须优先使用：

- 用户视角断言。
- schema 校验。
- 明确业务结果。
- 稳定 test id 或可访问性 selector。
- fake timer。
- deterministic fixture。
- 独立测试数据工厂。
- 测试后清理。
- targeted E2E。
- 合约驱动 mock。

如果发现 flaky test，必须定位根因，不允许简单增加 retry 掩盖问题。

## 真实环境兼容性要求

前端功能必须考虑真实用户环境，而不是只在开发者浏览器可用。

必须检查：

1. Chrome。
2. Safari，如项目面向 Mac/iOS 用户。
3. Firefox，如项目要求。
4. 移动端 375px。
5. 平板 768px。
6. 桌面 1440px。
7. 慢网络。
8. 请求失败。
9. 浏览器刷新。
10. 后退/前进导航。
11. 多标签页。
12. 系统暗色模式。
13. 系统缩放。
14. 中文输入法。
15. 长文本。
16. 超长文件名。
17. 不同时区。
18. 不同语言长度，如项目支持 i18n。

关键用户旅程至少要在桌面和移动端验证。


## 时间、金额、国际化与边界格式

所有涉及时间、金额、数量、语言、文件名、单位的功能必须额外检查。

必须检查：

1. 时间统一存储格式。
2. 显示时区是否明确。
3. 到期时间边界。
4. 跨天、跨月、闰年。
5. 金额不能用 float 直接计算。
6. 积分、额度、次数必须使用整数或精确 decimal。
7. 货币单位明确。
8. 前后端金额单位一致。
9. 长文本不会撑爆布局。
10. 中文、英文、数字、emoji、特殊字符输入。
11. 文件名特殊字符。
12. 排序规则。
13. 空字符串和 null 的区别。
14. 日期筛选边界包含关系。

## 产品分析与用户反馈闭环

SaaS 产品需要验证用户是否真的顺利使用，而不仅是功能存在。

核心用户旅程应考虑埋点或事件记录：

1. 页面访问。
2. 关键按钮点击。
3. 表单提交。
4. 表单校验失败。
5. 任务创建。
6. 任务成功。
7. 任务失败。
8. 重试。
9. 支付开始。
10. 支付成功。
11. 支付失败。
12. 用户完成 onboarding。
13. 用户触达核心价值事件。

埋点要求：

- 不记录敏感数据。
- 不记录完整 prompt、密钥、支付信息。
- 事件命名统一。
- 能按用户、租户、版本、时间维度分析。
- 失败事件必须包含抽象错误码。
- 不暴露上游供应商信息。

最终交付时，如涉及核心流程，必须说明是否需要产品埋点和漏斗分析。

## 事故响应与业务连续性

生产级 SaaS 必须考虑事故响应。

必须评估：

1. 核心服务不可用时用户看到什么。
2. 外部 API 不可用时是否降级。
3. 数据库不可用时是否有明确错误。
4. 队列积压时是否有告警。
5. 任务失败是否可重试。
6. 用户误删是否可恢复。
7. 密钥泄露是否可轮换。
8. 支付 webhook 丢失是否可补偿。
9. 生成任务卡住是否可取消或恢复。
10. 发布失败是否可回滚。
11. 是否有 runbook。
12. 是否有 incident 记录模板。

最终报告必须列出：

- 当前最大单点故障。
- 当前恢复手段。
- 当前无法自动恢复的风险。
- 建议补充的 runbook。

## 需求可追溯矩阵

所有任务必须维护需求可追溯矩阵，确保用户提出的每一个点都有明确处理状态。

矩阵字段：

- 用户原始需求点。
- 需求分类：功能 / UI / UX / 安全 / 性能 / 测试 / 文档 / 运维 / 数据库 / 成本 / 合规。
- 优先级：MUST / SHOULD / COULD / WONT。
- 对应 spec。
- 对应 plan。
- 对应 tasks。
- 对应代码文件。
- 对应测试文件。
- 对应验证命令。
- 当前状态：未开始 / 进行中 / 已实现 / 已验证 / 阻塞 / 不做。
- 证据。
- 剩余风险。

最终交付时必须逐项回填，不允许只用总结性语言声称“都完成了”。

如果某个需求点没有实现，必须明确说明：

- 为什么没实现。
- 是否需要用户确认。
- 影响范围。
- 替代方案。
- 后续任务建议。

## 业务不变量与领域模型

开发前必须识别业务不变量。业务不变量是系统在任何情况下都必须保持成立的规则。

必须为核心领域定义：

1. 实体。
2. 状态。
3. 状态转移。
4. 权限边界。
5. 额度规则。
6. 计费规则。
7. 租户隔离规则。
8. 数据一致性规则。
9. 删除和恢复规则。
10. 失败补偿规则。

示例不变量：

- 用户不能访问其他租户的数据。
- 额度不能被并发请求扣成负数。
- 同一个幂等请求不能产生重复副作用。
- 支付未成功不能发放权益。
- webhook 重复投递不能重复发放权益。
- 任务终态只能是 succeeded / failed / cancelled / timeout 之一。
- 已删除资源不能被普通用户继续访问。
- 管理员操作必须审计。
- 外部 API 失败不能导致本地数据进入不可恢复状态。

每个核心不变量必须至少有一种验证方式：

- 单元测试。
- 集成测试。
- 数据库约束。
- E2E 测试。
- 代码审查证据。
- 运行时断言。
- 监控告警。

禁止只依赖前端 UI 保证业务不变量。后端和数据库必须作为最终边界。

## API 版本化与向后兼容

如果项目包含公开 API、移动端、小程序、浏览器插件、第三方集成或长期运行的客户端，必须检查 API 版本化和兼容性。

必须遵守：

1. 不随意删除字段。
2. 不随意改变字段类型。
3. 不随意改变错误码。
4. 不随意改变分页结构。
5. 不随意改变鉴权方式。
6. 新字段应尽量向后兼容。
7. 废弃字段必须有 deprecation 计划。
8. 破坏性变更必须提升版本。
9. API contract 必须有测试。
10. 前端和后端必须共享 schema 或进行合约校验。

最终报告必须说明：

- 本次是否改变 API。
- 是否兼容旧客户端。
- 是否需要版本号。
- 是否需要迁移说明。
- 是否需要通知用户或第三方开发者。

## Feature Flag、Kill Switch 与灰度实验

高风险功能必须评估是否需要 feature flag 或 kill switch。

适用场景：

- AI 生成。
- 视频生成。
- 图片生成。
- 支付。
- 批量导入。
- 批量删除。
- 新计费逻辑。
- 新权限系统。
- 新数据库迁移。
- 新外部 API provider。
- 新 onboarding 流程。
- 新 UI 大改版。

要求：

1. 可以按环境开启。
2. 可以按租户开启。
3. 可以按用户开启。
4. 可以按百分比灰度。
5. 可以快速关闭。
6. 关闭后用户看到合理降级提示。
7. 关闭后不会破坏已有数据。
8. 开关状态必须可观测。
9. kill switch 不应依赖正在故障的同一个服务。
10. feature flag 本身不能泄露内部供应商信息。

最终交付时必须说明：

- 是否需要 feature flag。
- 是否需要 kill switch。
- 默认开启还是关闭。
- 回滚方式。
- 降级文案。

## CI/CD 质量门禁

本地验证必须尽量转化为 CI/CD 自动门禁，避免只依赖人工或 Agent 当次执行。

CI 至少应包含：

1. install with lockfile。
2. typecheck。
3. lint。
4. unit tests。
5. integration tests。
6. coverage threshold。
7. build。
8. security audit。
9. dependency license check，如项目支持。
10. targeted E2E 或 smoke E2E。
11. migration check，如涉及数据库。
12. API contract check。
13. mock contract check。
14. bundle size check，如前端项目适用。
15. preview deploy smoke test，如平台支持。

PR 合并条件：

- 所有 required checks 通过。
- P0/P1 缺陷为 0。
- 数据库迁移已审查。
- 安全敏感变更已审查。
- 真实 API 调用风险已确认。
- 文档已同步。
- 验证台账已更新。

如果项目暂无 CI，必须在报告中建议最小 CI 配置。

## 数据迁移、回填与对账

所有数据库迁移、批量更新、数据回填都必须按生产风险处理。

必须检查：

1. 是否向前兼容。
2. 是否可回滚。
3. 是否会锁表。
4. 是否会长事务。
5. 是否会影响线上写入。
6. 是否需要分批执行。
7. 是否支持暂停和恢复。
8. 是否幂等。
9. 是否有 dry-run。
10. 是否有执行前统计。
11. 是否有执行后对账。
12. 是否有失败重试策略。
13. 是否有备份。
14. 是否影响多租户隔离。
15. 是否会误删数据。

回填任务必须记录：

- batch size。
- cursor。
- processed count。
- failed count。
- skipped count。
- startedAt。
- finishedAt。
- error summary。
- reconciliation result。

禁止在没有备份、没有对账、没有回滚策略的情况下执行破坏性生产数据操作。


## 缓存一致性与失效策略

如果项目使用缓存、CDN、ISR、SWR、Redis、浏览器缓存、React Query、SWR、服务端缓存，必须检查缓存一致性。

必须明确：

1. 缓存 key 如何设计。
2. 是否包含 tenant / user / permission scope。
3. TTL 是多少。
4. 何时失效。
5. 写操作后如何更新缓存。
6. 删除后如何清理缓存。
7. 权限变化后缓存是否失效。
8. 套餐变化后权限缓存是否失效。
9. 用户退出后敏感缓存是否清理。
10. 是否会缓存错误响应。
11. 是否会缓存空结果。
12. 是否存在缓存击穿。
13. 是否存在缓存雪崩。
14. 是否存在缓存穿透。
15. 是否存在脏读风险。

禁止跨租户共享未隔离缓存 key。

关键权限、计费、额度、用户身份相关数据必须谨慎缓存。

## 套餐、权益与配额系统

如果项目涉及免费版、专业版、企业版、积分、额度、订阅、用量限制，必须检查权益系统。

必须明确：

1. 套餐包含哪些能力。
2. 每个能力的限制。
3. 限制维度：用户 / 租户 / workspace / 月 / 日 / 单次。
4. 额度如何扣减。
5. 额度何时返还。
6. 并发请求如何防超用。
7. 套餐升级何时生效。
8. 套餐降级如何处理已有数据。
9. 订阅过期如何处理。
10. 支付失败如何处理。
11. 退款如何处理。
12. 取消订阅如何处理。
13. webhook 重复如何处理。
14. 管理员手动调整是否审计。
15. 前端展示和后端限制是否一致。

后端必须作为最终权益判断边界，不能只靠前端隐藏功能。

测试必须覆盖：

- 免费用户访问付费能力。
- 额度不足。
- 额度刚好用完。
- 并发消耗额度。
- 失败返还。
- 重复提交。
- 套餐升级。
- 套餐降级。
- 订阅过期。

## 客户支持与诊断能力

核心业务必须考虑客服和技术支持如何定位用户问题。

必须评估是否需要：

1. 用户诊断 ID。
2. requestId 搜索。
3. jobId 搜索。
4. tenantId 搜索。
5. 最近错误记录。
6. 最近任务状态。
7. 最近支付状态。
8. 最近 webhook 状态。
9. 最近额度变更。
10. 最近权限变更。
11. 操作审计日志。
12. 可导出的诊断包。

诊断包必须脱敏，不得包含：

- token。
- API key。
- 密码。
- 完整支付信息。
- 私密文件内容。
- 未授权租户数据。
- 上游供应商敏感信息。

最终交付报告应说明用户报错时如何定位问题。

## 用户帮助、Onboarding 与产品文案

SaaS 产品必须降低用户理解成本。功能不仅要可用，还要让新用户知道怎么用。

必须检查：

1. 新用户是否知道第一步做什么。
2. 空状态是否有引导。
3. 错误状态是否有下一步。
4. 高成本操作是否有确认。
5. 长任务是否解释等待原因。
6. 专业术语是否有解释。
7. 危险操作是否有二次确认。
8. 成功状态是否引导下一步。
9. 是否需要示例数据。
10. 是否需要模板。
11. 是否需要帮助链接。
12. 是否需要快捷入口。
13. 是否需要首次使用引导。
14. 是否需要 tooltip。
15. 是否需要文档中心。

文案原则：

- 面向用户结果，不面向技术实现。
- 不暴露上游供应商。
- 不使用“演示”“测试”“mock”等面向内部的词。
- 错误文案不甩锅给用户。
- 失败时给出可执行下一步。

## 可访问性 WCAG 门禁

前端交付必须尽量满足 WCAG 2.1 AA 基线。

必须检查：

1. 所有交互元素可键盘访问。
2. 焦点状态清晰可见。
3. 弹窗有焦点陷阱。
4. 弹窗关闭后焦点返回触发元素。
5. 表单字段有 label。
6. 错误信息和字段关联。
7. 图片有 alt，装饰图例外。
8. 颜色对比满足 AA。
9. 不只依赖颜色传达状态。
10. loading 状态可被辅助技术感知。
11. toast 不应是唯一错误反馈。
12. 页面有合理 landmark。
13. heading 层级合理。
14. aria 属性正确，不滥用。
15. 动画尊重 prefers-reduced-motion。

E2E 或 QA 中必须至少验证关键路径的键盘操作。

## 浏览器存储与会话安全

所有浏览器端存储必须经过安全审查。

必须检查：

1. 是否在 localStorage 存 token。
2. 是否在 localStorage 存敏感用户数据。
3. 是否在 URL query 中暴露 token。
4. 是否在错误监控中上传敏感状态。
5. 是否在缓存中保存跨租户数据。
6. logout 后是否清理本地状态。
7. 多标签页 logout 是否同步。
8. session 过期后 UI 是否正确跳转。
9. refresh token 是否安全。
10. cookie 是否 HttpOnly / Secure / SameSite。
11. CSRF 是否防护。
12. XSS 时本地数据是否有泄露风险。

原则：

- 服务端密钥绝不进前端。
- 认证 token 优先使用 httpOnly cookie。
- 本地缓存必须按用户和租户隔离。
- 登出必须清理敏感本地状态。

## 威胁建模与滥用场景

安全审查必须包含威胁建模，而不只是常规漏洞扫描。所有核心功能必须从攻击者、恶意用户、越权用户、异常租户、脚本机器人、内部误操作的角度审查。

必须使用 STRIDE 或等价方法检查：

1. Spoofing：身份伪造。
2. Tampering：参数篡改、数据篡改。
3. Repudiation：操作不可追溯。
4. Information Disclosure：信息泄露。
5. Denial of Service：拒绝服务、资源耗尽。
6. Elevation of Privilege：权限提升。

必须额外检查业务滥用：

- 免费额度刷爆成本。
- 高成本接口被脚本批量调用。
- 重复点击产生重复订单、重复任务、重复扣费。
- 越权访问其他用户或租户数据。
- 修改请求参数绕过套餐限制。
- 邀请链接、分享链接、重置密码链接被枚举或重放。
- webhook 被伪造、重放或乱序投递。
- 文件上传被用于存储恶意内容。
- prompt injection 获取系统提示词或内部策略。
- API key 泄露后无限调用。
- 管理员误操作造成大规模数据破坏。

每个高风险功能必须输出：

- 资产。
- 攻击面。
- 攻击者能力假设。
- 可能滥用路径。
- 已有防护。
- 缺口。
- 测试或验证方式。
- 剩余风险。

## 企业身份体系与访问控制

如果项目面向企业客户，必须评估企业身份体系。

必须检查：

1. 是否支持 SSO。
2. 是否支持 SAML 或 OIDC。
3. 是否支持 MFA。
4. 是否支持强制 MFA。
5. 是否支持 SCIM 用户自动同步。
6. 是否支持企业域名自动加入或限制。
7. 是否支持成员邀请。
8. 是否支持邀请过期。
9. 是否支持撤销邀请。
10. 是否支持角色管理。
11. 是否支持自定义角色，如项目需要。
12. 是否支持离职成员权限回收。
13. 是否支持 session 失效。
14. 是否支持设备/session 管理。
15. 是否支持管理员审计日志。

权限检查必须在后端执行，不能只依赖前端隐藏按钮。

必须测试：

- 未登录访问。
- 普通用户访问管理员接口。
- A 租户用户访问 B 租户资源。
- 被移除成员继续使用旧 session。
- 角色降级后访问旧权限。
- 邀请链接过期。
- 邀请链接重复使用。
- SSO 用户与密码用户绑定冲突，如适用。

## API Key、OAuth 与机器身份安全

如果项目提供开放 API、自动化集成、SDK、CLI、Webhook 或机器访问能力，必须设计机器身份安全。

必须检查：

1. API key 只在创建时展示一次。
2. 服务端只存 hash，不存明文。
3. API key 必须可撤销。
4. API key 支持过期时间。
5. API key 支持 scope。
6. API key 绑定 tenant / organization。
7. API key 支持 last used time。
8. API key 支持命名，便于用户识别。
9. API key 支持轮换。
10. API key 调用必须限流。
11. API key 权限不能超过创建者或租户授权范围。
12. 删除或禁用后必须立即失效。
13. 日志和错误监控不得记录完整 API key。
14. UI 中只能显示前缀和后四位。
15. 开放 API 必须有稳定错误码。

如使用 OAuth，必须检查：

- redirect_uri 精确匹配。
- state 参数防 CSRF。
- PKCE，如公共客户端适用。
- access token 过期。
- refresh token 轮换。
- scope 最小权限。
- revoke token。
- consent 页面清楚。

## 出站 Webhook 与第三方集成

如果系统向客户或第三方发送 webhook，必须保证可靠、安全、可诊断。

必须检查：

1. webhook 事件必须有 eventId。
2. webhook payload 必须有 eventType、createdAt、tenantId 或等价上下文。
3. webhook 必须签名。
4. 签名密钥必须可轮换。
5. webhook 必须异步发送，不能阻塞核心请求。
6. webhook 必须有重试策略。
7. webhook 必须有最大重试次数。
8. webhook 必须有 dead-letter 或失败记录。
9. webhook 必须支持手动重放，如项目需要。
10. webhook 必须记录响应状态码和耗时。
11. webhook 不得发送超出客户授权的数据。
12. webhook 订阅必须按事件类型过滤。
13. webhook endpoint 必须支持禁用。
14. webhook 失败不能导致核心交易重复执行。
15. webhook 文档必须说明签名验证和重试策略。

测试必须覆盖：

- 正常发送。
- 目标服务 500。
- 目标服务超时。
- 目标服务返回 429。
- 签名验证。
- 重试。
- 最大重试后失败记录。
- 手动重放。

## 文件上传、存储与内容安全

如果项目支持文件上传、图片上传、视频上传、导入导出、附件、头像、素材库，必须进行文件安全审查。

必须检查：

1. 文件大小限制。
2. 文件数量限制。
3. MIME 类型白名单。
4. 扩展名白名单。
5. 文件头 magic number 校验。
6. 文件名安全处理，禁止路径穿越。
7. SVG、HTML、PDF 等主动内容风险。
8. 压缩包炸弹风险。
9. 图片处理资源消耗风险。
10. 文件存储路径包含 tenant/user scope。
11. 私有文件不能公开访问。
12. 下载接口必须鉴权授权。
13. 删除业务对象时关联文件如何处理。
14. 上传失败是否清理临时文件。
15. 是否需要病毒扫描。
16. 是否需要内容审核。
17. 是否需要文件过期策略。
18. 是否需要 CDN 缓存失效。
19. 是否需要 signed URL。
20. signed URL 是否有短过期时间。

测试必须覆盖：

- 超大文件。
- 错误类型。
- 伪造 MIME。
- 空文件。
- 特殊字符文件名。
- 重复文件名。
- 未授权下载。
- 跨租户下载。
- 删除后访问。

## 邮件、短信与通知系统

如果项目涉及邮件、短信、站内信、Push、任务通知、账单通知，必须检查通知系统可靠性和成本。

必须检查：

1. 通知发送必须异步化。
2. 必须有发送状态记录。
3. 必须有失败重试。
4. 必须有最大重试次数。
5. 必须防重复发送。
6. 短信和邮件验证码必须限流。
7. 密码重置链接必须短期过期。
8. 邀请链接必须可撤销和过期。
9. 通知模板不能暴露内部技术或上游供应商。
10. 通知不得包含敏感密钥或完整隐私数据。
11. 用户营销类通知应支持退订，如适用。
12. 交易类通知和营销类通知必须区分。
13. 多语言模板必须有 fallback。
14. 邮件发送失败必须可诊断。
15. 高成本短信必须有成本保护。
16. 邮件链接必须防 open redirect。
17. 通知偏好必须尊重用户设置。

测试必须覆盖：

- 正常发送。
- 发送失败。
- 重复触发。
- 限流。
- 过期链接。
- 撤销链接。
- 模板变量缺失。
- 恶意链接参数。

## 事件驱动、一致性与补偿事务

如果系统涉及异步任务、队列、webhook、支付、通知、积分、生成任务、跨服务调用，必须评估一致性模型。

必须检查：

1. 哪些操作需要强一致。
2. 哪些操作可以最终一致。
3. 是否需要 Outbox Pattern。
4. 是否需要 Saga。
5. 是否需要补偿事务。
6. 是否需要幂等消费。
7. 是否需要消息去重。
8. 是否需要事件顺序控制。
9. 是否允许状态回退。
10. 是否有死信队列。
11. 是否有失败重放。
12. 是否有对账任务。
13. 是否有状态修复脚本。
14. 是否有事件审计表。
15. 是否避免在数据库事务中调用外部 API。

关键原则：

- 数据库事务内不要直接调用不可靠外部服务。
- 外部事件必须幂等处理。
- 异步任务必须可重试。
- 终态任务不能被旧事件覆盖。
- 支付、额度、权益必须可对账。

## 发布健康指标与自动回滚

每次发布后必须观察健康指标，不应只看部署成功。

必须定义发布后观察窗口：

- 5 分钟。
- 15 分钟。
- 30 分钟。
- 1 小时。

必须观察：

1. 5xx 错误率。
2. API p95 延迟。
3. 前端 JS 错误率。
4. 关键任务失败率。
5. 登录成功率。
6. 支付/webhook 成功率，如适用。
7. 生成任务成功率，如适用。
8. 数据库连接数。
9. 队列积压。
10. 外部 API 错误率。
11. rate limit 异常。
12. 业务核心转化事件。

必须设置回滚触发条件：

- P0 错误出现。
- 5xx 错误率超过阈值。
- 核心路径成功率明显下降。
- p95 延迟超过阈值。
- 队列积压持续增长。
- 付费或生成成本异常增长。
- 监控显示数据写入异常。

最终报告必须说明：

- 发布后需要观察哪些指标。
- 哪些指标触发回滚。
- 如何回滚。
- 谁负责确认。

对于核心 SaaS 链路，必须评估故障注入测试或手工演练。

必须模拟或设计应对：

1. 数据库超时。
2. 数据库连接耗尽。
3. 缓存不可用。
4. 队列不可用。
5. 外部 API 500。
6. 外部 API 超时。
7. 外部 API rate limit。
8. 文件存储失败。
9. 邮件/短信发送失败。
10. webhook 投递失败。
11. 前端网络断开。
12. 用户刷新页面。
13. 多标签重复提交。
14. 部署中断。
15. 部分服务降级。

要求：

- 故障时用户看到清楚提示。
- 高成本任务不会无限重试。
- 系统不会产生重复扣费或重复权益。

SaaS 必须用 SLO 描述可靠性，而不是口头承诺“稳定”。

必须为核心链路定义或建议：

3. 错误率目标。
4. 任务成功率目标。
5. 任务完成时间目标。
6. 队列积压阈值。
7. 数据恢复目标 RPO。
8. 服务恢复目标 RTO。
9. 最大并发用户假设。
10. 最大租户规模假设。
11. 最大数据量假设。
12. 最大文件大小假设。
13. 最大任务并发假设。

如果用户未提供目标，必须使用保守默认假设，并在报告中标记需要用户确认。

必须输出：

- 当前容量瓶颈。
- 可水平扩展部分。
- 不可水平扩展部分。
- 单点故障。
- 下一个容量拐点。
- 扩容方案。

## 测试数据管理

测试数据必须可重复、可隔离、可清理，禁止依赖真实用户数据。

必须检查：

4. 是否有固定随机种子。
5. 每个测试是否隔离租户和用户。
6. 测试后是否清理。
7. E2E 是否使用专用测试账号。

10. fixture 是否脱敏。

## 高级测试技术

对于核心安全、计费、权限、解析、导入、额度、状态机、schema validation，必须评估高级测试方法。

### Property-based Testing

适用于：

- 额度计算。
- 金额计算。
- 日期边界。
- 权限组合。
- 状态机。
- 分页。
- 排序。
- 数据转换。
- parser。
- import validation。

必须验证不变量，例如：

- 额度永不为负。
- 分页不会重复或遗漏。
- 状态终态不可逆。
- 金额计算无浮点误差。
- 越权请求始终拒绝。

### Fuzzing

适用于：

- 用户输入。
- 文件名。
- CSV/Excel 导入。
- JSON API。
- 搜索查询。
- prompt。
- webhook payload。
- URL 参数。
- 富文本。

必须测试畸形、超长、特殊字符、空值、嵌套过深、非法编码。

### Mutation Testing

对于关键逻辑，如权限、计费、额度、状态机，若项目支持，应评估 mutation testing，确保测试能真正发现逻辑错误，而不是只追求覆盖率数字。

## 风控、反滥用与反欺诈

必须检查：

1. 注册频率限制。

## 客户健康度与续费风险

13. 客户反馈入口。
14. NPS 或满意度，如项目需要。
15. 客户成功后台，如项目需要。

## 企业级 SaaS 第三批高级门禁

### 1. 威胁建模

核心功能必须做威胁建模，覆盖身份伪造、参数篡改、抵赖、信息泄露、拒绝服务、权限提升，以及业务滥用、成本滥用、跨租户访问、脚本刷接口、webhook 重放、prompt injection 等场景。

### 2. 企业身份

面向企业客户时，必须评估 SSO、SAML/OIDC、MFA、SCIM、成员邀请、角色管理、session 失效、离职权限回收和审计日志。权限必须由后端强制执行。

### 3. 机器身份

开放 API 或自动化集成必须审查 API key / OAuth。API key 只能创建时显示一次，服务端只存 hash，必须支持撤销、过期、scope、tenant 绑定、last used、轮换和限流。

### 4. 出站 Webhook

出站 webhook 必须有 eventId、签名、重试、最大重试次数、失败记录、手动重放、响应状态记录和 payload 最小化。不得阻塞核心请求。

### 5. 文件安全

文件上传必须校验大小、数量、MIME、扩展名、magic number、文件名安全、权限、租户隔离、signed URL、删除策略、病毒扫描和内容审核需求。测试必须覆盖跨租户下载和删除后访问。

### 6. 通知系统

邮件、短信、站内信、Push 必须异步化、防重复、限流、可重试、可诊断。验证码、密码重置、邀请链接必须过期、可撤销、防枚举、防重放。

### 7. 一致性模型

异步任务、队列、webhook、支付、通知、生成任务必须明确强一致或最终一致。必要时使用 Outbox、Saga、补偿事务、幂等消费、死信队列和对账任务。

### 8. 发布健康和回滚

发布后必须观察 5xx、p95、前端错误率、核心任务成功率、队列积压、外部 API 错误率、成本异常。必须定义回滚触发条件。

### 9. 故障注入

核心链路必须评估数据库超时、缓存不可用、队列不可用、外部 API 500、外部 API 超时、文件存储失败、webhook 失败、网络断开等故障场景。失败必须可恢复、可诊断、可告警。

### 10. SLO 与容量

必须为核心链路定义或建议可用性、延迟、错误率、任务成功率、RPO、RTO、最大并发、最大数据量、最大文件大小和扩容路径。

### 11. 测试数据

测试数据必须可重复、可隔离、可清理。禁止使用真实生产数据。E2E 必须使用专用测试账号和 deterministic fixture。mock 必须符合 schema。

### 12. 高级测试

核心权限、计费、额度、状态机、导入、解析、schema validation 必须评估 property-based testing、fuzzing 和 mutation testing，确保测试能发现真实逻辑错误。

### 13. 视觉回归

UI 改动必须复用设计系统，避免重复造组件。关键页面应在 375px、768px、1440px 保存或对比截图，检查布局、暗色模式、可访问性和视觉一致性。

### 14. 数据导入导出

CSV/Excel/JSON 导入导出必须处理大小限制、字段校验、dry-run、部分失败、错误报告、异步进度、CSV 注入、敏感字段脱敏、下载链接过期和审计日志。

### 15. 租户生命周期

多租户 SaaS 必须支持或评估租户创建、成员管理、owner 转移、套餐变化、冻结、恢复、删除、导出、迁移、合并、审计和租户级限流。

### 16. 白标和自定义域名

如支持白标或自定义域名，必须检查 DNS 验证、TLS、domain tenant binding、CORS、cookie domain、canonical、og:url、品牌资源安全和域名接管风险。

### 17. 反滥用风控

必须检查注册、登录、密码重置、邀请、免费额度、高成本 API、API key、租户用量的异常检测、限流、冻结、误伤申诉和管理员处理能力。

### 18. 客户健康度

核心 SaaS 应评估激活事件、核心价值事件、任务成功率、功能采用率、额度使用率、团队活跃度、续费风险、流失预警和客户反馈入口。

### 19. 技术债

每次变更必须评估技术债，记录债务描述、风险、偿还建议和不偿还后果。禁止默认接受“以后再清理”。

### 20. 架构 Fitness Functions

项目应尽量通过自动化规则保护架构边界，例如禁止无 schema 的 API、禁止无分页列表、禁止跨租户查询缺少 tenant scope、禁止真实外部 API 在测试中调用、禁止敏感日志、禁止前端导入服务端 secret。

## 终极 SaaS 全生命周期补充门禁

本项目不只按“功能完成”标准交付，而是按企业级 SaaS 全生命周期标准审查。除代码、测试、E2E、mock、安全、性能、UI/UX、数据库、运维之外，还必须按风险触发以下门禁。

---

### 1. 产品战略与商业闭环

任何功能开发前，必须理解它服务的产品目标，而不是只实现代码。

必须检查：

1. 目标用户是谁。
2. 用户的核心痛点是什么。
3. 该功能解决哪个 Job To Be Done。
4. 对应的核心价值事件是什么。
5. 是否推动激活、留存、转化、续费或扩张。
6. 是否影响新用户 onboarding。
7. 是否影响企业客户采购。
8. 是否影响付费套餐差异。
9. 是否会增加支持成本。
10. 是否会增加用户理解成本。
11. 是否有明确成功指标。
12. 是否有失败判断指标。

核心指标应考虑：

- 激活率。
- 首次价值达成时间。
- 转化率。
- 留存率。
- 任务成功率。
- 生成成功率。
- 付费转化。
- 续费率。
- 扩容率。
- 工单率。
- 失败率。
- 成本/收入比。

禁止只从工程角度判断功能完成。最终报告必须说明该功能如何帮助用户达成业务目标。


### 2. 商业化、定价、发票与财务正确性

如果项目涉及订阅、套餐、积分、额度、支付、发票、退款、优惠券、试用期、企业合同，必须进行商业化专项审查。

必须检查：

1. 免费版、专业版、企业版权益是否清楚。
2. 试用期开始和结束规则。
3. 试用期是否需要支付方式。
4. 套餐升级是否立即生效。
5. 套餐降级是否延迟到周期结束。
6. 取消订阅后权益如何变化。
7. 支付失败后的宽限期。
8. dunning 催款流程。
9. 退款后权益是否回收。
10. chargeback 如何处理。
11. 优惠券是否可叠加。
12. 优惠券是否可滥用。
13. 发票信息是否正确。
14. 税费 VAT/GST/Sales Tax 是否考虑。
15. 货币单位是否一致。
16. 金额计算是否使用 decimal 或整数最小单位。
17. 是否避免浮点误差。
18. 是否支持企业账期或手动开票，如业务需要。
19. 是否需要收入确认或财务对账。
20. 支付 webhook 是否幂等。

测试必须覆盖：

- 试用开始。
- 试用结束。
- 套餐升级。
- 套餐降级。
- 支付成功。
- 支付失败。
- 退款。
- 重复 webhook。
- 并发扣费。
- 额度不足。
- 失败返还。
- 优惠券边界。
- 订阅过期。

后端必须作为最终权益判断边界，不能只靠前端展示套餐差异。

### 3. 法务、隐私、Cookie 与用户协议

如果功能涉及用户数据、行为分析、支付、AI 处理、文件上传、第三方服务、企业客户数据，必须评估法务和隐私影响。

必须检查：

1. 是否新增数据收集。
2. 是否新增敏感数据处理。
3. 是否新增第三方数据处理方。
4. 是否需要更新隐私政策。
5. 是否需要更新用户协议。
6. 是否需要 Cookie 同意。
7. 是否涉及营销 Cookie。
8. 是否涉及分析 Cookie。
9. 是否支持用户撤回同意。
10. 是否支持数据导出。
11. 是否支持数据删除。
12. 是否支持账号注销。
13. 是否支持 DSAR 数据主体请求。
14. 是否有数据保留周期。
15. 是否有数据删除证明。
16. 是否存在跨境传输。
17. 是否涉及未成年人数据。
18. 是否涉及医疗、金融、教育等敏感行业。
19. 是否涉及企业客户合同约束。
20. 是否有子处理商清单。

禁止：

- 未经用户同意收集不必要数据。
- analytics 上传完整 prompt、文件内容、支付信息、token、密钥。
- 错误监控上传敏感 payload。
- 测试 fixture 使用真实用户数据。
- 在日志中记录敏感内容。

最终报告必须说明：

- 本次是否影响隐私政策。
- 是否新增第三方处理方。
- 是否新增敏感数据。
- 是否需要用户同意。
- 是否存在合规风险。

### 4. 合规控制映射

如果项目面向企业客户，必须考虑合规控制，不只是写功能。

根据项目行业和客户要求，评估：

- SOC2。
- ISO27001。
- GDPR。
- CCPA。
- PIPL。
- 等保。
- HIPAA，如涉及医疗。
- PCI DSS，如直接处理支付卡数据。
- SOX，如涉及上市公司财务系统。
- FedRAMP，如涉及美国政府客户。

必须将关键能力映射到控制项：

1. 访问控制。
2. 最小权限。
3. 审计日志。
4. 密钥管理。
5. 加密。
6. 变更管理。
7. 漏洞管理。
8. 备份恢复。
9. 事故响应。
10. 供应商管理。
11. 员工访问审查。
12. 数据保留。
13. 数据删除。
14. 安全培训，如组织层面适用。
15. 业务连续性。

工程交付应产生可审计证据：

- 测试报告。
- 审计日志截图或说明。
- 权限模型文档。
- 数据流图。
- 威胁模型。
- 备份策略。
- 事故响应流程。
- 依赖审查结果。
- 安全扫描结果。
- 变更记录。

不能声称“符合某合规认证”，除非组织已真实完成认证。正确表述是：本次变更已按对应控制要求进行设计和证据记录。

### 5. 云基础设施与 IaC

如果项目涉及部署、云资源、数据库、存储、队列、CDN、DNS、负载均衡、Serverless、Kubernetes，必须审查云基础设施。

必须检查：

1. 是否使用 IaC，例如 Terraform、Pulumi、CDK。
2. 生产、预发、开发环境是否隔离。
3. 环境变量是否完整。
4. 云 IAM 是否最小权限。
5. CI/CD 凭证是否最小权限。
6. 数据库是否私有网络访问。
7. 存储桶是否默认私有。
8. CDN 是否配置缓存策略。
9. WAF 是否需要。
10. DDoS 防护是否需要。
11. egress 出站访问是否可控。
12. 是否需要 IP allowlist。
13. 是否有资源标签用于成本归属。
14. 是否有预算告警。
15. 是否有日志保留策略。
16. 是否有备份策略。
17. 是否有灾备区域。
18. 是否有健康检查。
19. 是否支持自动扩缩容。
20. 是否避免单点故障。

禁止：

- 生产数据库暴露公网。
- 存储桶公开敏感文件。
- CI 使用过宽权限。
- 多环境共用生产密钥。
- 手工创建不可追踪的关键资源。

最终报告必须说明：

- 是否涉及云资源变化。
- 是否需要 IaC 更新。
- 是否有成本影响。
- 是否有权限风险。
- 是否有回滚方案。

### 6. 容器、Kubernetes 与运行时安全

如果项目使用 Docker、Kubernetes、容器平台或 Serverless，必须检查运行时安全。

必须检查：

1. 镜像是否最小化。
2. 镜像是否扫描漏洞。
3. 是否使用固定版本 tag。
4. 是否避免 latest tag。
5. 容器是否非 root 用户运行。
6. 文件系统是否只读，如可行。
7. 是否设置 CPU / memory limit。
8. 是否设置 readiness probe。
9. 是否设置 liveness probe。
10. 是否支持 graceful shutdown。
11. 是否正确处理 SIGTERM。
12. 是否避免请求中断导致数据不一致。
13. 是否设置 request timeout。
14. 是否有水平扩缩容策略。
15. 是否有 PodDisruptionBudget，如 K8s 适用。
16. 是否有 NetworkPolicy，如 K8s 适用。
17. 是否隔离 secret。
18. 是否避免 secret 进入镜像层。
19. 是否配置日志输出。
20. 是否避免本地磁盘保存关键状态。

Serverless 还必须检查：

- 冷启动影响。
- 最大执行时间。
- 并发限制。
- 重试语义。
- 幂等。
- 连接池。
- 外部 API 超时。

### 7. 加密、KMS 与密钥生命周期

所有敏感数据和密钥必须有生命周期管理，而不是只放环境变量。

必须检查：

1. 传输中是否使用 TLS。
2. 静态数据是否加密。
3. 敏感字段是否需要字段级加密。
4. 是否使用 KMS 或等价密钥管理。
5. 密钥是否可轮换。
6. 密钥轮换是否不会导致旧数据不可读。
7. 是否有密钥版本。
8. 是否有密钥访问审计。
9. 是否有密钥泄露应急流程。
10. 是否有 secret rotation 计划。
11. 是否有 CI secret 保护。
12. 是否有生产 secret 最小访问权限。
13. 是否避免 secret 出现在构建日志。
14. 是否避免 secret 出现在前端 bundle。
15. 是否避免 secret 出现在错误监控。
16. 是否避免 secret 出现在测试报告。
17. 是否有 break-glass 访问流程。
18. 是否定期审查密钥使用。
19. 是否能撤销泄露 token。
20. 是否有 API key hash 存储。

禁止明文存储长期敏感密钥。

### 8. 备份、PITR 与灾难恢复

备份存在不等于能恢复。必须验证恢复能力。

必须检查：

1. 是否开启数据库备份。
2. 是否支持 Point-in-Time Recovery。
3. 备份频率。
4. 备份保留周期。
5. 备份是否加密。
6. 备份是否跨区域。
7. 备份访问权限。
8. 是否定期恢复演练。
9. 是否记录恢复时间。
10. 是否有 RPO。
11. 是否有 RTO。
12. 文件存储是否有备份。
13. 配置和 secret 是否有恢复方案。
14. IaC 是否能重建环境。

### 30. 自动化安全边界与人工审批

4. 退款。
5. 发放权益。

9. 执行数据库迁移。

12. 访问跨租户数据。
13. 轮换密钥。
14. 修改 DNS。
15. 发布生产版本。

原则：

- 优先 dry-run。
- 优先可回滚。
- 优先最小范围。
- 优先人工确认。
- 所有危险操作必须审计。



## 23. ## Release Gate：最终交付门禁

只有通过 Release Gate，才能声明任务完成。

### 1. 代码门禁

- 没有伪实现。
- 没有 TODO 代替逻辑。
- 没有省略代码。
- 没有无关重构。
- 没有重复造轮子。
- 没有未使用代码。
- 没有调试日志。
- 没有硬编码 secret。
- 没有暴露上游供应商。
- 没有破坏现有 API 合约。

### 2. 测试门禁

必须运行并记录：

- 相关单元测试。
- 相关集成测试。
- 相关合约测试。
- targeted E2E。
- typecheck。
- lint。
- build。
- coverage，如项目支持。
- 安全扫描，如项目支持。
- 小规模并发或幂等验证，如涉及后端写入、高成本任务、队列或支付。

不能运行的命令必须说明原因、影响和替代验证方式。

### 3. Mock 门禁

- 所有付费外部 API 已 mock。
- mock 通过 schema 或合约校验。
- mock 覆盖成功、失败、超时、限流、异常响应。
- 没有未授权真实调用。
- 真实 API 调用次数为 0，除非用户明确授权。
- mock fixture 已集中管理。
- mock 与 E2E、集成测试尽量复用。

### 4. 用户体验门禁

- 核心路径可完整完成。
- 每个关键点击有反馈。
- loading 明确。
- success 明确。
- error 可恢复。
- empty 有引导。
- forbidden / unauthorized 合理。
- 表单校验清楚。
- 长任务有状态。
- 重复提交被防护。
- 移动端关键路径可用。
- 无 critical console error。
- 无关键布局溢出。
- 不暴露内部技术或上游供应商。

### 5. 后端与数据库门禁

- 输入验证完整。
- 鉴权完整。
- 授权完整。
- 查询有租户隔离，如 SaaS 项目适用。
- 列表有分页。
- 高频查询评估索引。
- 无明显 N+1。
- 写操作考虑事务或一致性。
- 高成本操作限流。
- 重复提交幂等。
- 错误响应不泄露内部细节。
- 日志脱敏。

### 6. 性能与并发门禁

- 核心页面加载和交互有明确反馈。
- 高成本任务异步化或有清晰等待体验。
- 轮询有停止条件。
- API 无无界查询。
- 并发重复请求不会产生重复副作用。
- 小规模并发验证通过，或明确说明未验证原因。
- 已记录性能风险和下一步压测建议。

### 7. 文档与交接门禁

必须更新：

- README，如命令、环境变量、使用方式变化。
- CLAUDE.md，如项目约定变化。
- docs/ONBOARDING.md，如架构或入口变化。
- API 文档，如接口变化。
- .env.example，如环境变量变化。
- 验证台账。
- benchmark 记录，如做了性能测试。
- 变更说明。

### 8. 最终报告必须包含

- 完成内容。
- 修改文件。
- 用户旅程验证。
- 测试命令和结果。
- 覆盖率。
- E2E 范围。
- mock 范围。
- 是否发生真实 API 调用。
- 安全审查。
- 性能审查。
- UI/UX 审查。
- 数据库审查。
- 已知剩余风险。
- 最有力反驳观点。
- 下一阶段主要矛盾。

## 元规则：风险驱动而非清单驱动

所有门禁都必须按风险触发。不要为了执行清单而做无关工作。每次任务先判断：

1. 本次改动影响哪些资产。
2. 影响哪些用户旅程。
3. 影响哪些数据。
4. 是否涉及钱、权限、隐私、成本、外部 API、数据库、异步任务、企业客户。
5. 哪些专项门禁必须启用。
6. 哪些门禁本次不适用，并说明原因。

最终报告必须区分：

- 已验证。
- 不适用。
- 未验证但有风险。
- 需要用户决策。
